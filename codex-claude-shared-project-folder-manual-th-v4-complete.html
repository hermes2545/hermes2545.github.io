SECTION 01

แนวคิดหลัก: เลิกเลือกระหว่าง ChatGPT กับ Claude

วิดีโอที่ส่งมามีชื่อ “I Stopped Choosing Between ChatGPT and Claude. Here's the Setup” — แก่นที่นำมาใช้ในคู่มือนี้คือการวาง AI หลายตัวบน project workspace เดียวกัน แทนการแยก project knowledge ไว้คนละแอป

วิธีเดิม: Platform-centric

ChatGPT มี project/context ของตัวเอง, Claude มี project/context ของตัวเอง แล้วคนต้องคอยคัดลอกข้อมูลระหว่างสองฝั่ง

ผลเสียข้อมูลเก่า, decision ไม่ตรงกัน, ไฟล์ซ้ำ, ไม่รู้ว่าอันไหนล่าสุด และ handoff พึ่งความจำของคน

วิธีใหม่: Folder-centric

ย้าย “ความจริงของโปรเจกต์” ออกจาก chat history มาอยู่ในไฟล์ Markdown และ source files ในโฟลเดอร์ที่ทั้งสอง agent เข้าถึงได้

ผลดีportable, audit ได้, backup ได้, Git ได้, เปลี่ยนโมเดลได้ และคนอ่านเองได้

Working protocol:
- Inspect before editing.
- Prefer small reversible changes.
- Run relevant tests after edits.

End of session:

SECTION 06

Workflow ใช้งานจริงในหนึ่งวัน

ใช้ ChatGPT และ Claude เป็นคนละบทบาทได้ แต่ห้ามให้บทบาทเป็นตัวกำหนด “ความจริง” คนละชุด

1. Readอ่าน Context + Status
→
2. Claimระบุงานที่จะทำ
→
3. Workแก้ไฟล์ / วิเคราะห์
→
4. Verifytests / review / diff
→
5. Handoffอัปเดต state

ตัวอย่าง: ChatGPT วางแผน → Claude ลงมือ

ChatGPT: อ่าน requirement, แตกงาน, อัปเดต proposed plan ใน handoff file โดยไม่แก้ source

Claude: อ่าน plan + source files, implement, test, อัปเดต status และ diff summary

ตัวอย่าง: Claude ทำ → ChatGPT Review

Claude: implement และทดสอบ

ChatGPT: อ่าน git diff + decision constraints, ทำ independent review และเขียน findings ลง review note

กติกาสำคัญอย่าให้ agent สองตัวแก้ไฟล์เดียวกันพร้อมกันโดยไม่ใช้ branch/worktree หรือ ownership rule เพราะ “shared folder” ไม่ได้แปลว่า “safe parallel editing”

SECTION 10

AI อ่านได้มากขึ้นเท่าไร ก็ต้องแบ่ง “ข้อมูลที่ควรรู้” กับ “credentials ที่ไม่ควรโหลดเข้าบริบท” ให้ชัดขึ้น

SECTION 11

Advanced Patterns สำหรับ project ใหญ่

เมื่อระบบโต ให้เพิ่มโครงสร้างโดยไม่ทำลายหลัก canonical + thin adapter

A. Hierarchical Context

มี root context สำหรับทั้ง project และไฟล์ context เฉพาะ subfolder เช่น src/backend/CLAUDE.md หรือ AGENTS.md ระดับย่อยเมื่อเครื่องมือรองรับ เพื่อเพิ่มคำสั่งเฉพาะพื้นที่

B. Role Separation

กำหนด Agent A = Implementer, Agent B = Reviewer โดย reviewer เป็น read-only จนกว่าจะพบ critical defect

C. Proposed vs Approved

AI เขียนข้อเสนอใน PROPOSALS.md; เฉพาะสิ่งที่คนอนุมัติแล้วจึงย้ายเข้า DECISIONS.md

D. Machine-readable State

ถ้าจะทำ automation เพิ่ม state.json หรือ YAML สำหรับ status ที่ script อ่านได้ แต่ยังมี Markdown สำหรับคน

Three-tier memory pattern

HotSTATUS / OPEN_LOOPS
อ่านทุก session
→
WarmPROJECT / RULES / DECISIONS
อ่านตาม task
→
Coldarchive / old sessions
ค้นเมื่อจำเป็น

Universal Project Migration Prompt

UNIVERSAL MIGRATION PROMPT
คุณได้รับเอกสาร HTML ชื่อ Shared Project Folder Manual ซึ่งอธิบายแนวทางการจัด Project Folder เพื่อให้ ChatGPT/Codex และ Claude Code สามารถทำงานบน Project เดียวกัน โดยใช้ข้อมูลกลางชุดเดียวกัน

ให้ใช้เอกสารนี้เป็น “Reference Architecture และ Implementation Guide” สำหรับตรวจสอบและปรับโครงสร้าง Project ปัจจุบัน

เป้าหมาย:
ทำให้ Project นี้สามารถใช้งานร่วมกันระหว่าง ChatGPT/Codex และ Claude Code ได้ โดยไม่ต้องคัดลอก Context ไปมาระหว่าง AI และให้ Project Folder เป็น Single Source of Truth

PHASE 1 — STUDY
1. อ่าน HTML Manual ทั้งหมดก่อน
2. แยกให้ออกว่าอะไรคือหลักการ อะไรคือตัวอย่าง และอะไรคือคำสั่งนำไปใช้จริง
3. อย่าคัดลอกเนื้อหาทั้ง Manual เข้า AGENTS.md หรือ CLAUDE.md

PHASE 2 — INSPECT
1. สำรวจโครงสร้าง Project ปัจจุบันทั้งหมด
2. ตรวจ README, docs, instructions, memory files, task/state files และ source code ที่เกี่ยวข้อง
3. ห้ามแก้ไขไฟล์ทันที
4. ระบุ:
   - มีอะไรอยู่แล้ว
   - ขาดอะไร
   - มีอะไรซ้ำซ้อน
   - Context ใดกระจัดกระจาย
   - ไฟล์ใดควรเป็น Canonical Context
   - มี instruction conflict หรือไม่
   - มีความเสี่ยงที่ AI สองตัวจะเขียนไฟล์ชนกันหรือไม่
   - มี Secrets/Credentials ปะปนในไฟล์ที่ AI จะอ่านหรือไม่

PHASE 3 — DESIGN
เปรียบเทียบโครงสร้างปัจจุบันกับ Manual และเสนอ “Migration Plan” โดยแบ่งเป็น:

A. Current Structure
B. Problems Found
C. Proposed Structure
D. Files to Create
E. Files to Modify
F. Files to Move
G. Files to Keep Unchanged
H. Context to Consolidate
I. Risks
J. Migration Steps
K. Rollback Plan

หลักการที่ต้องรักษา:
- Project Folder เป็น Single Source of Truth
- ChatGPT/Codex และ Claude ใช้ Canonical Project Context ชุดเดียวกัน
- หลีกเลี่ยงการเก็บ Project Facts ซ้ำใน AGENTS.md และ CLAUDE.md
- Canonical Context ควรอยู่ใน context/ หรือพื้นที่กลางที่เหมาะสมกับ Project เดิม
- AGENTS.md เป็น Adapter สำหรับ ChatGPT/Codex
- CLAUDE.md เป็น Adapter สำหรับ Claude Code
- Adapter ต้องบางและชี้ไปยังข้อมูลกลาง
- ต้องมี Current Status, Decisions, Open Loops และ Handoff
- ห้ามเก็บ Secrets หรือ Credentials ใน Shared Context
- Preserve Git history ถ้ามี
- หลีกเลี่ยง destructive changes
- อย่าลบไฟล์เดิมจนตรวจสอบแล้วว่า migrate ข้อมูลครบ
- อย่าเปลี่ยน architecture ที่ไม่เกี่ยวข้องกับ Shared AI Context โดยไม่มีเหตุผล
- ถ้า Project ปัจจุบันมีโครงสร้างที่ดีกว่า Manual ให้รักษาโครงเดิมและ Adapt แนวคิดเข้าไปแทน

PHASE 4 — STOP FOR REVIEW
ก่อนดำเนินการจริง:
- แสดง Proposed Migration Plan
- แสดง Files Impacted
- แสดง Risks
- แสดงสิ่งที่ต้องให้มนุษย์ตัดสินใจ
- ยังไม่แก้ไขไฟล์จนกว่าจะได้รับคำสั่งให้ดำเนินการ

PHASE 5 — IMPLEMENT
หลังได้รับอนุญาต:
1. สร้างหรือแก้ไฟล์ที่จำเป็น
2. Preserve เนื้อหาเดิม
3. Consolidate Context ที่ซ้ำกัน
4. สร้าง/ปรับ AGENTS.md และ CLAUDE.md ให้เป็น Thin Adapter
5. สร้าง Shared Context ที่จำเป็น
6. สร้าง Handoff mechanism
7. ตรวจ links และ paths
8. ตรวจ .gitignore / secrets handling
9. Run relevant validation/tests
10. สรุป diff และสิ่งที่เปลี่ยนแปลง

PHASE 6 — VERIFY SHARED CONTEXT
ทดสอบว่า AI ทั้งสองสามารถตอบคำถามต่อไปนี้จาก Source เดียวกัน:

1. Project นี้มีเป้าหมายอะไร
2. Current Goal คืออะไร
3. งานล่าสุดทำถึงไหน
4. Decision ล่าสุดคืออะไร
5. มี Open Loops อะไร
6. Next Action คืออะไร
7. มี Blocker อะไร
8. กติกาสำคัญของ Project คืออะไร

Expected result:
คำตอบของ ChatGPT/Codex และ Claude ควรสอดคล้องกันในข้อเท็จจริง แม้วิธีวิเคราะห์หรือรูปแบบคำตอบจะแตกต่างกันได้

หากพบข้อมูลขัดแย้ง:
- ห้ามเดา
- ระบุไฟล์ที่ขัดแย้งกัน
- ระบุว่า Source ไหนน่าจะเป็น Canonical
- ขอการตัดสินใจจากมนุษย์หากไม่สามารถตัดสินได้จาก Project เอง

บทนี้ใช้เมื่อ Project ไม่ได้เริ่มจากศูนย์ แต่เคยถูกสร้างหรือพัฒนามาแล้วด้วย Claude, ChatGPT/Codex หรือทั้งสองฝั่งแยกกัน จุดประสงค์คือย้ายเข้าสู่ Shared Project Folder โดยไม่ทำข้อมูลเดิมสูญหาย ไม่เลือก version ผิด และไม่ทำให้ AI ฝั่งหนึ่งกลายเป็น Source of Truth โดยอัตโนมัติ

กฎสูงสุดของ Existing Project Migration ห้ามถือว่า Project ฝั่ง Claude, ChatGPT/Codex, chat history, memory, timestamp ล่าสุด หรือไฟล์ที่ดู “ใหม่กว่า” เป็นฝ่ายถูกโดยอัตโนมัติ หากข้อมูลขัดแย้งกัน ต้องเข้าสู่ Reconciliation ก่อน และต้องขอ Human Approval เมื่อไม่สามารถพิสูจน์ได้จากหลักฐานใน Project

ทำไม Project เดิมเสี่ยงกว่าการเริ่มใหม่

Project เดิมอาจมีคำสั่งซ้อนกัน, Context ซ้ำ, Decision คนละเวอร์ชัน, ไฟล์ source ต่าง revision, memory ที่ยังไม่เคยถูกเขียนลงไฟล์ และกติกาที่ถูกฝังอยู่ใน chat history ของ AI แต่ละตัว

Decision State ที่ต้องใช้ระหว่าง Migration

Decision status model
PROPOSED
- AI หรือมนุษย์เสนอ แต่ยังไม่อนุมัติ

APPROVED
- มนุษย์หรือ authority ที่กำหนดไว้ยืนยันแล้ว

SUPERSEDED
- เคย Approved แต่ถูกแทนด้วย Decision ใหม่

REJECTED
- พิจารณาแล้วและไม่ใช้

UNVERIFIED
- มาจาก memory/chat/history แต่ยังไม่มีหลักฐานเพียงพอ

CONFLICTED
- มี source มากกว่าหนึ่งชุดที่ขัดแย้งและยังหาข้อสรุปไม่ได้

EXISTING PROJECT MIGRATION SAFETY PROTOCOL

Project นี้มีประวัติการใช้งานมาก่อน อาจเคยทำงานด้วย Claude, ChatGPT/Codex หรือทั้งสองฝั่งแยกกัน

ให้ถือว่าการย้ายครั้งนี้เป็น “Reconciliation + Migration” ไม่ใช่การสร้าง Project ใหม่

NON-DESTRUCTIVE RULES
1. ห้ามลบ ย้าย เขียนทับ หรือ rename ไฟล์เดิมใน Phase แรก
2. ห้ามถือว่า Project ของ AI ฝั่งที่คุณกำลังรันอยู่เป็น Source of Truth โดยอัตโนมัติ
3. ห้ามเลือก version จาก timestamp ล่าสุดเพียงอย่างเดียว
4. ห้าม merge Decision ที่ขัดแย้งกันเอง
5. ห้ามถือ AI memory, chat history หรือ summary เก่าเป็น verified fact โดยไม่ตรวจหลักฐาน
6. ห้าม overwrite CLAUDE.md หรือ AGENTS.md เดิมก่อนทำ instruction inventory
7. ห้ามนำ secrets, tokens, credentials หรือ private keys เข้าสู่ Shared Context
8. ห้ามลบ Project เดิมหลัง migration จนกว่าจะผ่าน final verification และได้รับ Human Approval

PHASE A — INVENTORY
สำรวจทุก source ที่เกี่ยวข้อง:
- Project folders
- CLAUDE.md
- AGENTS.md
- README / docs
- STATUS / TODO / task files
- DECISIONS / ADR / architecture docs
- source code
- tests
- Git branches / tags / commits ถ้ามี
- session notes / handoffs
- exported chat summaries หรือ memory ที่ผู้ใช้ให้มา
- uploaded knowledge ที่ยังมีผลกับ Project

สร้าง Inventory โดยระบุ:
- path/source
- ประเภทข้อมูล
- last modified / commit ถ้ามี
- provenance
- confidence
- duplicate with
- conflict with
- candidate canonical source

PHASE B — CLASSIFY
จัดข้อมูลแต่ละรายการเป็น:
- CANONICAL CANDIDATE
- DUPLICATE
- STALE
- SUPERSEDED
- UNVERIFIED
- CONFLICTED
- SECRET / DO NOT MIGRATE
- ARCHIVE ONLY

อย่าเปลี่ยนสถานะเป็น CANONICAL เพียงเพราะ source นั้นใหม่กว่า

PHASE C — COMPARE PROJECT VERSIONS
ถ้ามี Project มากกว่าหนึ่งชุด:
1. เปรียบเทียบ directory structure
2. เปรียบเทียบ relevant source files
3. เปรียบเทียบ Git history / branches ถ้ามี
4. เปรียบเทียบ tests และ build status
5. เปรียบเทียบ project instructions
6. เปรียบเทียบ decisions
7. เปรียบเทียบ current status / open work
8. เปรียบเทียบ assumptions และ constraints

สร้าง Reconciliation Matrix:
- SAME
- ONLY IN CLAUDE SIDE
- ONLY IN CHATGPT SIDE
- DIFFERENT BUT COMPATIBLE
- CONFLICT
- UNKNOWN

PHASE D — HUMAN DECISION GATE
ต้องหยุดและขอ Human Approval หากพบ:
- competing APPROVED decisions
- source revisions ที่ทั้งสองฝั่งดู valid
- architecture choices ที่ขัดกัน
- deletion of historically important files
- changes to security policy
- ambiguous ownership
- memory-only facts ที่มีผลต่อ Project
- migration ที่อาจทำให้ backward compatibility เสีย

แสดง conflict แบบเป็นกลาง:
- Source A says...
- Source B says...
- Evidence for A...
- Evidence for B...
- Impact if choosing A...
- Impact if choosing B...
- Recommended choice (ถ้ามี) พร้อมเหตุผล
- Human decision required: YES

PHASE E — MIGRATION PLAN
ก่อนแก้ไฟล์ ให้เสนอ:
1. Canonical structure
2. Canonical files
3. Adapter changes
4. Context consolidation map
5. Archive plan
6. Files to preserve unchanged
7. Files to deprecate later
8. Conflict resolutions already approved
9. Unresolved items
10. Rollback strategy
11. Verification strategy

PHASE F — IMPLEMENT AFTER APPROVAL
หลังได้รับอนุมัติ:
- ทำ migration แบบ incremental
- preserve original content
- ใช้ Git commits/checkpoints ถ้ามี
- ทำ backup/archive ของ instruction/context files ที่สำคัญก่อน replace
- สร้าง Shared Context
- ปรับ CLAUDE.md และ AGENTS.md เป็น Thin Adapters
- ย้ายเฉพาะ verified facts เข้าสู่ Canonical Context
- เก็บ UNVERIFIED/CONFLICTED items แยก ไม่ปะปนกับ approved facts
- update provenance หรือ decision history เมื่อเหมาะสม

PHASE G — VERIFY
ทดสอบทั้ง Claude และ ChatGPT/Codex แยกกัน โดยให้ตอบจาก Shared Project Folder:
- Project goal
- Current goal
- Latest approved decision
- Current status
- Open loops
- Next action
- Blockers
- Critical project rules

จากนั้นเปรียบเทียบคำตอบ:
- Factual consistency ต้องตรงกัน
- Differences in style/reasoning ยอมรับได้
- ถ้าข้อเท็จจริงต่างกัน ให้ถือว่า migration ยังไม่ผ่าน

FINAL SAFETY RULE
อย่าลบ Project เดิม, memory export, old adapters หรือ archive จนกว่า:
1. Shared Context verification ผ่าน
2. tests/build ที่เกี่ยวข้องผ่าน
3. unresolved conflicts ถูกปิด
4. Human ได้ตรวจ migration summary
5. Human อนุมัติการ retire/archive ของ source เดิม

AI Handoff Rule

MODEL-AGNOSTIC HANDOFF RULE
When taking over work created by another AI:

1. Do not assume the previous AI was correct.
2. Do not assume the previous AI was wrong.
3. Read the canonical project context first.
4. Inspect the actual files, tests, Git state, and approved decisions.
5. Treat previous-agent notes as evidence, not unquestionable truth.
6. Identify unresolved assumptions before editing.
7. Preserve existing architecture unless the task requires changing it.
8. If you disagree with an approved decision, report the concern; do not silently reverse it.
9. Verify your own changes before updating STATUS.md.
10. Leave a handoff that another capable AI can continue without needing your private chat history.
Portability Test Shared Project Architecture ถือว่าผ่านในระดับสำคัญเมื่อ AI ที่ไม่ได้สร้าง Project สามารถเปิด Project Folder, อ่าน instructions/context, อธิบายสถานะปัจจุบันได้ถูกต้อง และทำ task ต่อได้โดยไม่ต้องให้มนุษย์เล่าประวัติ Project ใหม่ทั้งหมด
