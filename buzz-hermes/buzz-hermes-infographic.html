L2BRIDGE

L3RUNTIME

L4MODEL

Model Provider

OpenRouter / Anthropic / OpenAI / Gemini / local model — Hermes เป็นคนเรียกตาม config ของ profile นั้น ไม่ได้ตั้งใน Buzz

ถ้า Buzz agent ต่อเข้า profile ที่ตั้งไว้ว่าใช้ OpenRouter → agent ตัวนั้นก็ใช้ model ผ่าน OpenRouter ตามที่ Hermes ตั้งไว้

ชั้นที่ 2

สะพานคือคำสั่งเดียว

ตรงนี้คือจุดที่ persona ตัวหนึ่งถูกผูกเข้ากับความสามารถชุดหนึ่ง เปลี่ยนคำเดียวหลัง --profile ก็เปลี่ยนทั้งความจำ เครื่องมือ และ model ที่ agent ตัวนั้นใช้

hermes acp --profile default

ถ้า Buzz ให้กรอกแยกช่อง

Command: hermes
Args: acp --profile default

เปลี่ยน profile = เปลี่ยน agent

ชื่อและ persona ยังเหมือนเดิม แต่ความจำ เครื่องมือ และสิทธิ์เปลี่ยนทั้งชุด

หมายเหตุ

รูปแบบคำสั่งจริงต้องปรับตามที่ Buzz ตั้ง runtime / ACP command ใน UI หรือ config

ชั้นที่ 3

Hermes ถืออะไร

ทุกอย่างที่เป็นความสามารถจริงและความเสี่ยงจริง — ของพวกนี้ต้องตั้งที่ Hermes ไม่ใช่เขียนใส่ persona

ส่วนของ Hermesความหมาย
Hermes ACPช่องทางให้ external app เรียก Hermes เป็น agent runtime
Hermes Profileขอบเขต memory, skills, config, tools, cron แยกเป็นชุด ๆ
Hermes Memoryความจำระยะยาวของ profile นั้น
Hermes Skillsprocedure / workflow ที่ agent โหลดมาใช้
Hermes Toolsความสามารถลงมือทำจริง เช่น terminal, files, browser, email
Hermes Model Configระบุว่าจะเรียก model / provider อะไร
Hermes Cronscheduled automations ของ profile นั้น

ความสามารถที่ persona ยืมมาใช้ได้ทันที

เมื่อ Buzz agent ต่อผ่าน ACP แล้ว ทุกอย่างด้านล่างนี้มาจาก Hermes ทั้งหมด ไม่ต้องตั้งซ้ำใน Buzz

#1 CONNECT

อยู่ได้ทุกช่องทาง

Telegram, Discord, Slack, WhatsApp, Signal, Email, CLI — agent เดียว ความจำเดียว ทุกหน้าจอ

#2 REMEMBER

ความจำถาวร

เรียนรู้ project ของเรา สร้าง skill ขึ้นเองอัตโนมัติ และไม่ลืมว่าเคยแก้ปัญหานั้นยังไง

#3 SCHEDULE

cron / automation

สั่งตารางงานด้วยภาษาธรรมดา ให้รายงาน backup หรือ briefing วิ่งเองผ่าน gateway

#4 DELEGATE

subagent แยกอิสระ

subagent มี conversation, terminal และ RPC script ของตัวเอง แตกงานได้โดยไม่กิน context

#5 SEARCH

ค้นเว็บ + ทำงานแทน

web search, browser automation, vision, image generation, TTS และ multi-model reasoning

#6 EXPERIMENT

sandbox แยกจากของจริง

local, Docker, SSH, Singularity, Modal — แยก namespace และ hardening ระดับ container

Hybrid profile strategy

แนวทางที่แนะนำ: เริ่ม 2 ชั้น

ไม่ต้องสร้างครบทุกตัวตั้งแต่แรก เพิ่มเมื่อเห็น pattern งานจริงแล้วเท่านั้น

1

Phase 1 — เริ่มแบบปลอดภัย ไม่ซับซ้อน

Buzz: Hermes Main→--profile default
Buzz: Hermes Sandbox→--profile buzz-sandbox

Main ใช้ memory / cron / skills ชุดเดิมที่ใช้ประจำอยู่แล้ว ส่วน Sandbox ไว้ทดลอง persona และ ACP โดยไม่แตะของจริง

2

Phase 2 — แยก specialist เมื่อใช้งานจริง

Buzz: Coding→--profile coding
Buzz: Research→--profile research
Buzz: Ops→--profile ops

ช่องทางเดิม (Telegram / LINE / Email / Google Chat) ยังวิ่งผ่าน Hermes Gateway เข้า profile default เหมือนเดิม

ทำไมต้องแยก profile

ถ้าทุก persona ใช้ default ร่วมกันหมด จะเจอ: memory หลาย persona ปนกัน · agent เฉพาะทางตอบปนบริบทของตัวอื่น · แยก tool permission ไม่ได้ · cron ปนกัน · ตั้ง model ต่างกันตามงานไม่ได้

Buzz persona

Hermes Sandbox

You are Hermes Sandbox, an experimental agent for testing Buzz/Hermes integration. Avoid production actions. Do not send emails, edit real tasks, or modify important files unless explicitly instructed.

Decision matrix

สถานการณ์ไหน ใช้ profile อะไร

สถานการณ์แนะนำให้ใช้เหตุผล
อยากให้ Buzz คุยกับ Hermes ตัวเดียวกับที่ใช้ประจำdefaultได้ memory / cron / skills ชุดเดียวกับ Hermes หลัก ถามต่อจากบริบทเดิมได้
อยากมีหลาย agent หลายบทบาทแยกตาม agentลด memory ปนกันและคุม tools ได้ง่าย
อยากทดลองก่อนbuzz-sandboxปลอดภัยกว่า ไม่กระทบของจริง
อยากให้ coding agent ใช้ tools เต็มcodingเปิด terminal / git / github ได้เฉพาะ profile นี้
อยากให้ research agent อ่านข้อมูลแต่ไม่ทำ action เสี่ยงresearchจำกัด tools เป็นแบบ read-oriented
มีคนอื่นอยู่ใน Buzz workspace ด้วยแยก + จำกัด toolsลดความเสี่ยงจาก prompt / agent misuse
Security model

persona ไม่ใช่กำแพงความปลอดภัย

Hermes มี tools ที่ลงมือทำจริงได้ ทั้ง terminal, file, email, browser จึงไม่ควรให้ทุก Buzz agent มีสิทธิ์เต็มเท่ากัน

❌ อย่าคิดแบบนี้

ตั้ง persona ว่า "ห้ามส่งอีเมล" แล้วถือว่าปลอดภัยพอ

✔ ควรคิดแบบนี้

ถ้าไม่อยากให้ส่งอีเมลจริง ก็ไม่ต้องเปิด email sending tools ใน profile นั้น

Anti-patterns

6 อย่างที่ควรเลี่ยง

Anti-patternทำไมไม่ดีทางเลือกที่แนะนำ
ทุก Buzz agent ใช้ default ร่วมกันmemory และ persona ปนกันMain ใช้ default, specialist ใช้ profile แยก
ใช้ persona เป็นตัวจำกัดสิทธิ์prompt ไม่ใช่ security boundaryจำกัด tools / credentials ที่ Hermes profile
เปิด terminal / email ให้ทุก agentเสี่ยงสั่งงานผิดหรือถูก prompt misuseเปิดเฉพาะ agent ที่จำเป็นจริง
ทดลองกับ profile หลักทันทีทำ memory / cron / config ปนกันใช้ buzz-sandbox ก่อน
clone profile พร้อม secrets ไปทุกที่credentials กระจายเกินจำเป็นให้แต่ละ profile มีเฉพาะ credentials ที่ใช้จริง
สร้าง agent เยอะตั้งแต่แรกdebug ยาก เข้าใจยากเริ่ม 2 ตัว แล้วค่อยเพิ่ม
Checklist

ก่อนเปิดใช้จริง

กดติ๊กได้เลยระหว่างทำจริง (สถานะไม่ถูกบันทึกไว้เมื่อปิดหน้า)

Hermes Main

  • Buzz agent ชี้ไป --profile default
  • ทดสอบถามเรื่องที่ default ควรรู้จาก memory
  • ทดสอบ tool ที่ปลอดภัย เช่น read-only หรือ query เบื้องต้น
  • ตรวจว่าไม่ได้เปิดให้คนอื่นใช้โดยไม่ตั้งใจ
  • ตรวจว่า cron หลักยังอยู่ profile เดิม

Specialist agent

  • สร้าง profile แยก เช่น coding / research / ops
  • ตั้ง model ให้เหมาะกับงาน
  • เปิดเฉพาะ toolsets ที่จำเป็น
  • เพิ่ม skills เฉพาะทาง
  • ไม่ clone secrets เกินจำเป็น
  • ทดสอบด้วยงานเล็กก่อน
  • ตั้ง persona ให้ตรงกับขอบเขต profile

ความปลอดภัย

  • เริ่มแบบ owner-only หรือ restricted users
  • ไม่ให้ Sandbox แตะ production tools
  • แยก profile ของ agent ที่ใช้ terminal / file write
  • แยก profile ของ agent ที่ใช้ email / asana / workspace
  • เลี่ยงการใช้ credentials ชุดเดียวกันทุก agent
  • ตรวจ log และผลลัพธ์หลังใช้งานครั้งแรก
