ถัดไป:
Foundation

Trust Line — งานที่ Agent ทำได้จริงโดยคุณไม่ต้องกลับมาตรวจ

ผู้เขียนเปลี่ยนวิธีวัด Agent จาก “ทำได้กี่อย่าง” เป็น “มีงานกี่ส่วนที่ฉันไว้ใจให้จบเองได้” เพราะงานที่อยู่เหนือเส้นความไว้ใจจะเด้งกลับมาเป็นงานตรวจของมนุษย์ทั้งหมด

1. Work

Agent ทำงานได้มากแค่ไหน — จำนวน Skills/Tools มีผลกับแกนนี้โดยตรง

2. Trust

คุณยอมรับผลลัพธ์ได้มากแค่ไหนโดยไม่ต้องตรวจซ้ำ — นี่คือแกนที่ผู้เขียนเคยมองข้าม

3. Autonomy

งานเกิดขึ้นได้มากแค่ไหนโดยไม่ต้องมีคุณเป็นคนเริ่มหรือคอยตอบคำถามระหว่างทาง

ทำไม “เพิ่ม Skill” อาจทำให้แย่ลง

สถานการณ์WorkTrustผลต่อคุณ
เพิ่ม Skills ต่อเนื่อง แต่ยังตรวจทุกอย่างสูงขึ้นเท่าเดิมAgent ผลิต “งานให้ตรวจ” มากขึ้น
ลด Scope แต่ตรวจผลลัพธ์ได้จริงอาจลดลงสูงขึ้นงานจบโดยไม่ย้อนกลับมาที่โต๊ะคุณมากขึ้น
วาง Gate ชัดและ schedule ได้คงที่/สูงสูงAutonomy เพิ่มโดยไม่เปิดความเสี่ยงแบบไร้ขอบเขต
คำถามวัด Trust Line
แทนที่จะถามว่า “Hermes ทำอะไรได้อีก?” ให้ถามว่า “งานที่ Hermes ทำอยู่ตอนนี้ ส่วนไหนที่ฉันยอมให้มันทำจบโดยไม่ตรวจได้?”

Upgrade 1

Stop Silent Failures — บังคับให้ Agent ตรวจ “สิ่งที่เกิดขึ้นจริง”

ขั้นแรกไม่ใช่เพิ่มความเร็ว แต่คือทำให้ Agent ไม่สามารถจบงานแบบเงียบ ๆ ทั้งที่ไม่มี artifact หรือผลลัพธ์จริง ผู้เขียนสรุปแนวทางเป็น 4 กลไกหลัก

1

Verification Rule

ก่อนรายงานว่างานสำเร็จ ให้เปิดสิ่งที่ผลิตขึ้นมาและตรวจเทียบกับคำขอ หากเปิดหรือตรวจไม่ได้ ให้ถือว่ายังพิสูจน์ความสำเร็จไม่ได้

2

Deterministic Code

ขั้นที่มี “คำตอบถูกเพียงแบบเดียว” โดยเฉพาะตัวเลข/ราคา/การคำนวณ ควรย้ายจาก prose instruction ไปเป็น script/code

3

Preconditions

เช็ก dependency ก่อนเริ่ม เช่น inbox เข้าถึงได้ไหม, pricing file มีอยู่ไหม, file ยังเป็นเดือนปัจจุบันหรือไม่ ถ้าไม่ผ่านให้หยุดแทนการเดา

4

Hooks + Harsh Success Checks

ถ้างานจบแล้ว “ไม่ได้ผลิตอะไร” ให้ถือเป็น failure และแจ้งเร็ว ไม่ใช่ success เพียงเพราะ flow เดินครบ

Operational verification rule

ข้อความด้านล่างเป็นเวอร์ชันสรุปเชิงปฏิบัติจากหลักการในต้นฉบับ ไม่ใช่คำพูดตรงแบบ verbatim

Skill rule
Before reporting success:
1) Open or retrieve the artifact/result you actually produced.
2) Compare it against the user's requested outcome.
3) Verify the real state, not your intended steps.
4) If you cannot inspect the result, do not claim success.
5) Report what you actually found, including failures or missing output.

Instruction หรือ Code?

ลักษณะงานใช้ Instructionใช้ Deterministic Code
มีหลายวิธีที่ “ถูก” ได้เหมาะ — ให้ Model ใช้วิจารณญาณอาจไม่จำเป็น
ต้องได้ผลเหมือนเดิมจาก input เดิมเสี่ยงต่อการ improviseเหมาะ
การเลือกอีเมลที่สำคัญเหมาะไม่ใช่กรณีหลัก
ยอดเงิน / ราคา / calculation ruleไม่ควรปล่อยให้ตีความใหม่ทุก runควรทำเป็น script
ประโยชน์แฝงของ Script
ต้นฉบับชี้ว่า script ไม่ต้องถูกโหลดเข้ามาเป็น reasoning context เหมือนคำสั่งยาว ๆ จึงได้ทั้ง consistency และ context efficiency

Precondition Checklist

  • External connection ที่งานต้องพึ่งพาใช้งานได้จริง
  • Required file / config มีอยู่และอ่านได้
  • ข้อมูลสำคัญไม่ stale เช่น pricing file เป็นเวอร์ชัน/เดือนปัจจุบัน
  • หาก prerequisite ใด fail ให้หยุดและรายงาน แทนการเติมช่องว่างด้วยการเดา
  • Success condition ต้องตรวจจาก output/state ที่เกิดขึ้นจริง

Upgrade 2

Approval Gate ไม่ได้ลด Autonomy — มันเป็นสิ่งที่ทำให้ Autonomy เกิดขึ้นได้

หาก Agent “ทำได้ทุกอย่าง” คุณต้องคอยเฝ้าทุกอย่าง แต่เมื่อมี hard boundary ที่มันจะไม่ข้าม คุณสามารถปล่อยให้สิ่งที่อยู่ฝั่งปลอดภัยทำงานต่อเองได้

AUTO — safe side

Agent ไปต่อเองได้

Answer questions Send information Ask for details Book a call
APPROVAL GATE — หยุดทันทีเมื่อข้ามเส้นนี้
HUMAN APPROVAL
Names / asks for price Commits to a date Promises a deliverable

Gate = Boundary

ขอบเขตชัดทำให้คุณรู้ว่าอะไร “ไม่มีวันถูก commit โดยอัตโนมัติ”

Schedule = Start Without You

ตัวอย่างของผู้เขียนใช้ cron ให้ workflow วิ่งทุกเช้า โดยไม่ต้องรอให้คนเริ่ม

Rollback = Safe Undo

Hermes snapshot ก่อนแก้ไฟล์และ rollback ได้ ผู้เขียนมองว่านี่ทำให้ “การลงมือ” ปลอดภัยขึ้น

Delivery channel มีผลต่อ Autonomy
ผู้เขียนส่งผลเข้า Telegram เพราะเป็นที่ที่เขาดูอยู่แล้ว แนวคิดคือ งานที่จบแต่ฝังอยู่ใน log ที่ไม่มีใครอ่าน เท่ากับงานที่ไม่ถูกใช้งาน

Approval Policy Template

Policy pattern
Proceed autonomously for low-risk, reversible actions.

STOP and request human approval before any action that:
- names or negotiates a price,
- creates a financial commitment,
- commits to a date or deadline,
- promises a deliverable,
- performs a public/irreversible action outside the approved boundary.
ลำดับสำคัญ
อย่าเริ่มจาก schedule/autonomy ก่อนแก้ Silent Failure เพราะคุณจะได้ระบบที่ “ผิดเร็วขึ้นและทำเองได้” แทนที่จะได้ระบบที่ไว้ใจได้

Upgrade 3

Restricted Subagents — เพิ่มความเร็วด้วยการแยก Context และ “เอา Tool ออก”

เมื่อ foundation ไว้ใจได้แล้ว ผู้เขียนจึงค่อยขยายด้วย subagents แต่เน้นว่า child agent ควรได้เฉพาะ Context และ Tools ที่จำเป็นสำหรับหน้าที่ของมัน

RULE

“อย่าส่งอีเมลนะ”

เป็นเพียงข้อความใน instruction ซึ่ง Model ต้องอ่านและปฏิบัติตาม จึงยังมี capability อยู่

VS
WALL

ไม่มี Send Tool ให้เลย

Agent ไม่สามารถส่งได้ในเชิง capability เพราะ Tool ไม่ถูกมอบให้ นี่คือ hard restriction ไม่ใช่คำขอให้ระวัง

ตัวอย่าง Email Subagent

ให้ทำ

  • Read inbox
  • Sort / classify messages
  • ทำงานใน context ของตัวเอง

ไม่ให้ Tool

  • Send messages
  • Write files
  • Spend money
Speed + Safety จากการเคลื่อนไหวเดียวกัน
Subagents ช่วยแยกงานที่เดิมทำเป็นเส้นตรงให้ขนานกันได้ ขณะเดียวกันการจำกัด Tools ทำให้ blast radius ของแต่ละ agent แคบลง

Principle of Least Capability

ให้ Subagent มี “เท่าที่ต้องใช้” ไม่ใช่ “ทุกอย่างที่ระบบมี”

30-second Skill Audit — เวอร์ชันใช้งาน

ถอดหลักการจาก prompt ในต้นฉบับและเรียบเรียงใหม่ให้สั้น/ชัดสำหรับนำไปใช้

Audit prompt
Audit my enabled Hermes skills.

1) Count every enabled skill.
2) Estimate the total tokens used by all enabled skill names and descriptions.
3) Report the context cost before I type a normal message.
4) List enabled skills not used in the last 30 days.
5) Recommend which skills to disable first, without deleting them.
เป้าหมายคือ Disable ไม่จำเป็นต้อง Delete
ผู้เขียนไม่ได้เสนอให้ลบ Skills ที่ไม่ได้ใช้ทั้งหมด แต่ให้ปิดไว้ก่อน แล้วค่อยเปิดเมื่อจำเป็น เพื่อให้ baseline context เบาลง

Apply in Order

Implementation Blueprint — แปลงแนวคิดให้เป็นระบบ Hermes ที่ใช้งานจริง

หน้านี้จัดโครงสร้างจากหลักการในต้นฉบับเป็น checklist เชิงปฏิบัติ โดยคงลำดับสำคัญ: Reliability ก่อน Autonomy และ Autonomy ก่อน Parallel Scale

1

เลือก Workflow ที่มีมูลค่าแต่ Scope ชัด

เช่น inbox triage/reply ไม่ต้องเริ่มจากงานที่ทำทุกอย่าง ให้เลือกงานซ้ำที่มี input/output มองเห็นได้

2

กำหนด Artifact / Success State

ระบุว่า “สำเร็จ” ต้องเห็นอะไรจริง เช่น draft ถูกสร้าง, message ถูกส่ง, file เปลี่ยนตามที่ขอ ไม่ใช่แค่ steps ผ่านครบ

3

ใส่ Verification Rule ทุก Skill ที่มี Action

ตรวจผลลัพธ์จากปลายทางจริง และห้าม claim success เมื่อเปิด/ตรวจ output ไม่ได้

4

ย้าย Exact Logic ไป Code

เลข, ราคา, formula และกฎ deterministic ควรอยู่ใน script เพื่อลดการ improvisation

5

เพิ่ม Preconditions + Failure Hooks

dependency fail ให้ stop; output ว่างให้แจ้ง failure; อย่าปล่อยให้ Agent “อ้อมช่องโหว่ด้วยการเดา”

6

ลาก Approval Boundary

เรื่องเงิน ราคา วันส่งมอบ คำมั่น หรือ public action ต้องหยุดรอมนุษย์ตาม policy

7

เปิด Schedule + Delivery Channel

เมื่อระบบพิสูจน์ตัวเองแล้ว จึงค่อยให้ cron เริ่มงานเอง และส่งผลไปช่องทางที่คุณดูจริง

8

แยก Restricted Subagents

แตกงานขนานและให้แต่ละ subagent มีเฉพาะ Context/Tools ที่ต้องใช้

9

เปิด Rollback / Snapshot

ทำให้ action ที่กระทบไฟล์ย้อนคืนได้ ลดต้นทุนของความผิดพลาด

10

Audit Skills / Context ทุกช่วง

ปิดสิ่งที่ไม่ใช้แทนการเก็บ capability ทุกอย่างไว้ active ตลอดเวลา

Definition of Done ที่สอดคล้องกับต้นฉบับ
ระบบพร้อมขยายเมื่อมัน บอกได้เมื่อ fail, ตรวจผลลัพธ์จริง, หยุดก่อนเรื่องสำคัญ, เริ่มงานเองได้ และความเสียหายย้อนกลับได้

Anti-patterns

4 Mistakes to Avoid

ข้อผิดพลาดที่ผู้เขียนสรุปท้ายวิดีโอสะท้อนหลักเดียวกันทั้งหมด: อย่าเพิ่ม capability ก่อนทำให้ระบบควบคุมและตรวจสอบได้

1

อย่าเปิด Skill เพราะมัน “ดูน่าใช้”

Skill ทุกตัวที่ enable มี context cost จึงควรเปิดเมื่อมันสร้างมูลค่าจริง ไม่ใช่เพราะอาจได้ใช้สักวัน

2

อย่าปล่อย Public / Financial Action โดยไม่มี Gate

เรื่องที่มีผลภายนอกหรือเรื่องเงินควรมี hard approval boundary

3

อย่าเชื่อ Success Report ที่พิสูจน์ Artifact ไม่ได้

ถ้า Agent เปิดสิ่งที่มันอ้างว่าสร้าง/ส่ง/แก้ไม่ได้ คุณยังไม่มีหลักฐานว่างานสำเร็จ

4

อย่าสลับลำดับ 3 Upgrades

Speed บนระบบที่ยังไว้ใจไม่ได้ คือความยุ่งเหยิงที่เดินทางมาถึงคุณเร็วขึ้น

Anti-pattern สั้นที่สุด
More Skills → More Speed → More Autonomy โดยไม่มี Verification และ Gate ไม่ใช่การ scale Agent แต่คือการ scale ความเสี่ยงและงานตรวจ

Cheat Sheet

Quick Reference — ตรวจ Hermes ใน 2 นาที

ใช้หน้านี้เป็น checklist อ้างอิงซ้ำก่อนเปิด automation ใหม่, schedule ใหม่ หรือเพิ่ม subagent

Reliability

ก่อน Agent บอกว่า “Done”

  • เปิดผลลัพธ์จริงแล้วหรือยัง?
  • ตรวจเทียบกับสิ่งที่ขอแล้วหรือยัง?
  • dependency ครบหรือยัง?
  • output ว่างถูกมองเป็น failure หรือยัง?
  • เลข/ราคา exact logic อยู่ใน code หรือยัง?
Approval

ก่อนเปิด Autonomy

  • เส้นที่ Agent ห้ามข้ามคืออะไร?
  • ราคา / เงิน / deadline / deliverable ถูก Gate หรือยัง?
  • ผลลัพธ์ถูกส่งไปที่ช่องทางที่คนดูจริงหรือไม่?
  • action สำคัญ rollback ได้หรือไม่?
Subagents

ก่อนแตกงานขนาน

  • แต่ละ agent มีหน้าที่เดียวชัดพอหรือยัง?
  • Context ถูกแยกเท่าที่จำเป็นหรือไม่?
  • Tools ที่ไม่จำเป็นถูกเอาออกจริงหรือยัง?
  • ใช้ “wall” แทน “rule” ในเรื่องสำคัญหรือไม่?
Context

ก่อนเพิ่ม Skill ใหม่

  • Skill นี้ใช้บ่อยแค่ไหน?
  • มันซ้ำกับของเดิมหรือไม่?
  • 30 วันที่ผ่านมา Skills ไหนไม่ถูกใช้?
  • ปิดไว้ก่อน แล้วเปิดเมื่อจำเป็นได้หรือไม่?

One-line Rules

หัวข้อRule
Successเชื่อ artifact/state ที่ตรวจได้ ไม่ใช่รายงานจาก intent
Exact Logicถ้ามีคำตอบถูกแบบเดียว ให้ code เป็นคนตัดสิน
Autonomyวางขอบเขตก่อน แล้วค่อยเดินเอง
SafetyCapability ที่ไม่มี ปลอดภัยกว่าคำสั่งว่า “อย่าใช้”
ScaleReliability → Gate → Parallelism
Contextทุก enabled skill ต้อง “จ่ายค่าเช่า” จึงควรเปิดเฉพาะสิ่งที่คุ้ม
