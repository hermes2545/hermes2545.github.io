ระบบความจำของ Hermes แบบหลายชั้น

เอกสารนี้อธิบายวิธีออกแบบ "ระบบความจำ" ให้ AI Agent (Hermes) ไม่ใช่แค่ "จำได้" แต่จำแบบมีโครงสร้าง — รวมแนวคิด Self-Improving Knowledge Base ที่ Agent ค่อย ๆ สะสมความรู้และปรับปรุงตัวเองจากงานที่ผ่านมา

memory หมวด 3

ระบบความจำมาตรฐานของ Hermes คืออะไร

Hermes มีความจำและ recall หลัก ๆ หลายแบบอยู่แล้ว:

forum 3.1 Conversation Context

ข้อความในบทสนทนาปัจจุบันที่ model เห็นอยู่ใน context window

check_circle เหมาะกับ
  • งานที่กำลังทำอยู่
  • คำถามล่าสุด
  • ไฟล์/output ที่เพิ่งเปิด
  • แผนงานใน session เดียว
cancel ไม่เหมาะกับ
  • ข้อมูลที่ต้องอยู่ถาวร
  • runbook ยาว ๆ
  • preference ที่ต้องใช้ทุกครั้ง

person 3.2 Persistent Memory / User Profile

memory ที่ถูก inject เข้ามาใน session ใหม่ เพื่อบอกข้อเท็จจริงถาวรเกี่ยวกับผู้ใช้หรือสภาพแวดล้อม ควรแยกเป็น 2 กลุ่ม:

account_circle User profile
  • ชอบให้ตอบภาษาอะไร
  • น้ำเสียงที่ต้องการ
  • ข้อห้ามส่วนตัว
  • preference ที่คงทน
settings Agent memory / environment
  • path สำคัญ
  • convention ของระบบ
  • tool quirks
  • ข้อควรระวังที่เจอซ้ำ
check_circle เหมาะกับ
  • preference ที่ยังจริงในอีกหลายเดือน
  • fact สั้น ๆ ที่ลดการถามซ้ำ
  • ข้อห้ามสำคัญ
  • environment convention ที่คงทน
cancel ไม่เหมาะกับ
  • งานที่ทำเสร็จแล้ว
  • issue/commit/PR number
  • log ยาว ๆ, รายชื่อไฟล์เยอะ ๆ
  • temporary TODO, architecture ยาว ๆ
Memory มาตรฐานควรเป็น "เข็มทิศ" ไม่ใช่ "คลังเอกสาร"

search 3.3 Session Search

การค้นหาบทสนทนาเก่า ๆ จาก database ของ Hermes

thumb_up ข้อดี
  • ไม่ต้องเก็บทุกอย่างใน memory
  • ย้อนดู decision เก่าได้
  • ใช้เป็น historical trace
thumb_down ข้อจำกัด
  • เป็น "ประวัติการคุย" ไม่ใช่ KB ที่ curate แล้ว
  • อาจมีข้อมูลผิด/ชั่วคราวปน
  • ต้องอ่านและสังเคราะห์ใหม่ทุกครั้ง
  • ไม่เหมาะเป็น single source of truth

build 3.4 Skills

Skill คือ procedural memory ของ Hermes — ขั้นตอนทำงานซ้ำ ๆ, command ที่พิสูจน์แล้ว, pitfall ของ tool, template, วิธี troubleshoot แบบเป็น pattern

rocket วิธี deploy service terminal แก้ systemd user service cloud ใช้ Google Workspace API rate_review วิธีทำ code review input ingest source เข้า wiki
thumb_up ข้อดี
  • โหลด skill เมื่องานตรง trigger
  • เก็บ procedure ละเอียดกว่า memory
  • ปรับปรุงได้เมื่อเจอ pitfall ใหม่
thumb_down ข้อจำกัด
  • ไม่ควรเป็น historical diary
  • ไม่ควรเก็บข้อมูล private มากเกินไป
  • ไม่เหมาะกับ architecture ยาวมาก ๆ สำหรับมนุษย์อ่าน

schedule 3.5 Cron Jobs / Automation State

ไม่ใช่ memory โดยตรง แต่เป็น stateful automation layer เหมาะกับ: ตรวจ inbox ทุกชั่วโมง, refresh dashboard, scrape feed, run health check, sync wiki ไป Drive

State ของ automation ควรอยู่ในไฟล์ state/manifest แยก เช่น:

.wiki/.ingestion/manifests/processed-files.json
.wiki/.ingestion/logs/healthcheck.json
warning
ไม่ควรเอา state เหล่านี้ไปใส่ memory มาตรฐาน เพราะจะเก่าเร็ว
warning หมวด 4

ข้อจำกัดของความจำมาตรฐาน

ระบบความจำมาตรฐานช่วยได้มาก แต่ยังมีข้อจำกัดเมื่อใช้กับงานระยะยาว

sd_card_alert 4.1 พื้นที่จำกัด

Persistent memory มีขนาดจำกัด ถ้าใส่เอกสารยาว จะเบียด preference สำคัญออก

format_clear 4.2 ขาดโครงสร้างเอกสาร

เป็นรายการสั้น ๆ ไม่เหมาะกับ diagram, runbook, decision log, installation guide, deep dive

edit_off 4.3 แก้/ตรวจสอบยาก

ข้อมูลยาว/ซ้ำ แก้ให้ถูกยากกว่าไฟล์ markdown ที่เปิดอ่านได้

help 4.4 ไม่มี provenance ชัด

มักไม่บอกว่า claim นี้มาจาก source ไหน เมื่อไหร่ ใครตัดสินใจ

running_with_errors 4.5 เสี่ยง "คำสั่งเก่า" ทับงานใหม่

ถ้าเขียน memory เป็น imperative:

Always run script X before doing Y.

อนาคต Agent อาจทำตามแม้สถานการณ์เปลี่ยนแล้ว — ควรเขียนเป็น declarative fact แทน:

Project A historically used script X for Y; verify current state before reuse.

กลไกการไหลของข้อมูล

input 8.1 Source ingestion flow

New source
  ▼  Capture raw source
  ▼  Classify source type
  ▼  Search existing wiki pages
  ├── related page exists ──► update page
  └── no related page ─────► page threshold met?
                              ├── yes ─► create synthesized page
                              └── no ──► keep only raw + log
  ▼  Update index.md
  ▼  Append log.md
  ▼  Optional mirror to Drive / Obsidian / Git

quiz 8.2 Query filing flow

User asks valuable question
  ▼  Agent searches wiki + session history if needed
  ▼  Agent answers user
  ▼  Is answer reusable / expensive to reconstruct?
  ├── no ──► do not file
  └── yes ─► create query page → update index → append log → optionally mirror

autorenew 8.3 Self-improvement flow

Task completed / bug fixed / workflow discovered
  ▼  Agent asks: What should be remembered?
  ├── user preference? ──────────► memory
  ├── repeatable procedure? ─────► skill
  ├── long reusable explanation? ► wiki
  ├── raw artifact? ─────────────► raw/
  └── temporary status? ─────────► session only / log only

rule 9.1 Decision rule — ถาม 5 ข้อ

จะยังจริงใน 3–6 เดือนไหม?
เป็น preference หรือ fact สั้น ๆ ไหม?
เป็น procedure ที่ต้องทำซ้ำไหม?
เป็นเอกสารยาวที่มนุษย์ควรเปิดอ่านไหม?
เป็น state ชั่วคราวของ automation ไหม?
  • preference → memory
  • procedure → skill
  • architecture/runbook/decision → wiki
  • raw source → raw/
  • processed state → .ingestion/
  • temporary progress → ไม่ต้องเก็บถาวร

ระดับความเป็นผู้ใหญ่ของระบบความจำ — ไล่จาก Level 0 ถึง Level 5

LV 0
No memory discipline
ทุกอย่างอยู่ใน chat history · ต้องถามซ้ำตลอด · ไม่มี runbook
LV 1
Persistent memory only

LV 2
Skills
procedure สำคัญถูกเก็บเป็น skill · ทำงานซ้ำได้ดีขึ้น แต่ long-form ยังไม่เป็นระบบ
LV 3
Wiki
มี SCHEMA/index/log · มี raw + synthesized layers · คำตอบสำคัญถูก filed
LV 4
Self-improving wiki
Agent update wiki หลังงานสำคัญ · มี health checks · query suggestions · dashboard · Drive/Obsidian mirror
LV 5
Knowledge operations system
automation รอบด้าน · review queue · provenance/contradiction tracking · public/private export pipeline · agent หลายตัวใช้ wiki เดียวกันได้

Short-term context
  ↓

  ↓
Session search
  ↓
Skills
  ↓
Self-improving wiki
  ↓
Raw archive + automation state
  ↓
