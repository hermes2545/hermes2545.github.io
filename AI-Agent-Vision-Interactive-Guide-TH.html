CHAPTER 00

0. เป้าหมาย ขอบเขต และกฎสำหรับ AI Agent

คู่มือนี้ใช้สร้างระบบที่:

  1. รับภาพจากกล้อง Tapo ที่รองรับ RTSP/ONVIF
  2. ใช้ Frigate ตรวจจับวัตถุ เช่น person, car, motorcycle
  3. ใช้ Zone เพื่อแจ้งเฉพาะพื้นที่สำคัญ เช่น หน้าประตูหรือทางรถเข้า
  4. ส่งภาพและข้อความไปยัง Home Assistant Companion App บน Android
  5. ให้ Android อ่านเสียง TTS โดยยังมีข้อความเป็น fallback
  6. เก็บ snapshot/recording ตามนโยบาย retention ที่กำหนด
  7. รองรับกล้องหนึ่งตัว หรือหลายตัวโดยไม่กล่าวอ้างว่าเป็นวัตถุเดียวกันหากไม่มีหลักฐาน
  8. เพิ่มการอ่านทะเบียน ประเภทรถ สี หรือยี่ห้อรถอย่างระมัดระวังผ่านโมเดลขั้นที่สอง

กฎที่ AI Agent ต้องปฏิบัติ

  • ห้ามเดา IP, username, password, token, entity ID, stream URL หรือพิกัด Zone
  • ห้ามใส่ secret ใน Git, log, screenshot, prompt หรือไฟล์สาธารณะ
  • ขอข้อมูลจากมนุษย์เฉพาะเมื่อจำเป็น และให้กรอก secret ลง secret store/local environment โดยตรง
  • สำรองไฟล์ก่อนแก้ทุกครั้ง และต้องมีวิธี rollback
  • เริ่มทีละกล้อง ทดสอบให้ผ่าน แล้วจึงเพิ่มกล้อง
  • ใช้ event/review ID จริงในการเรียก snapshot หรือ clip ห้ามจับคู่เหตุการณ์ด้วยเวลาอย่างเดียว
  • แยก “ตรวจพบวัตถุ” ออกจาก “ระบุตัวตน/ยี่ห้อ/รุ่น” อย่างชัดเจน
  • ผลจาก OCR, classifier หรือ Vision LLM ต้องมี confidence และเส้นทาง unknown
  • ห้ามใช้ผล AI เพียงอย่างเดียวเพื่อปลดล็อกประตู เปิดไม้กั้น กล่าวหา หรือระบุตัวบุคคล
  • หลังการเปลี่ยนแปลงต้องอ่านสถานะจริง ตรวจ log และทดสอบผลลัพธ์ปลายทาง
CHAPTER 01

บทที่ 1 — สิ่งที่มนุษย์ต้องเตรียม

1.1 รายการอุปกรณ์

อุปกรณ์จำเป็น

  • เครื่องสำหรับ Home Assistant
    • ง่ายที่สุด: อุปกรณ์ที่ติดตั้ง Home Assistant OS มาแล้ว
    • ทางเลือก DIY: เครื่อง x86-64, Raspberry Pi ที่รองรับ หรือ VM ตามเอกสาร Home Assistant
  • เครื่องสำหรับ Frigate
    • แนะนำ x86-64 ที่รองรับ Linux/Docker และมี iGPU/GPU/NPU/AI accelerator ที่ Frigate รองรับ
    • ระบบขนาดเล็กอาจใช้เครื่องเดียวกับ Home Assistant แต่การแยกเครื่องทำให้จัดสรร GPU, storage และการบำรุงรักษาง่ายกว่า
  • กล้อง Tapo แบบใช้ไฟต่อเนื่องที่รุ่นนั้นรองรับ RTSP/ONVIF
  • Ethernet switch/router และสาย Ethernet สำหรับ server
  • พื้นที่เก็บข้อมูลสำหรับวิดีโอ แนะนำ SSD/NVMe หรือดิสก์ที่เหมาะกับงานเขียนต่อเนื่อง
  • โทรศัพท์ Android ที่ติดตั้ง Home Assistant Companion App
  • เครื่องสำรองไฟ UPS สำหรับ server, switch และกล้องที่สำคัญ

อุปกรณ์เสริม

  • AI accelerator หรือ GPU/NPU ที่ Frigate รองรับ
  • VLAN สำหรับแยกกล้อง IoT
  • NAS สำหรับ backup/export ระยะยาว
  • กล้องตัวที่สองเพื่อช่วยมุมอับและยืนยันทิศทาง

1.2 ข้อควรรู้ก่อนซื้อกล้อง Tapo

  • กล้อง Tapo แบบใช้ไฟต่อเนื่องส่วนใหญ่รองรับ RTSP และ ONVIF Profile S แต่ต้องตรวจรุ่นและ hardware revision ก่อนซื้อ
  • กล้องแบตเตอรี่/โซลาร์ส่วนใหญ่ไม่มี stream ต่อเนื่อง จึงไม่เหมาะกับ Frigate แบบ NVR
  • เอกสารปัจจุบันระบุข้อยกเว้นกล้องประตูบางรุ่นที่ใช้ RTSP ได้เมื่อเดินไฟ เปิด always-on mode และติดตั้งอุปกรณ์ตามเงื่อนไขของผู้ผลิต
  • ONVIF Profile S ไม่รวม two-way audio จึงอย่าคาดหวังว่าการพูดกลับผ่านกล้องจะใช้ได้จาก RTSP/ONVIF
  • Tapo จำกัดจำนวน local viewers และบางรุ่นจำกัดการใช้ Tapo Care, storage ในกล้อง และ NVR พร้อมกัน ควรตรวจ FAQ ของรุ่นนั้น
  • ต้องสร้าง Camera Account ในแอป Tapo สำหรับ RTSP/ONVIF ซึ่งแยกจากบัญชี TP-Link cloud

1.3 การประเมินขนาดเครื่อง

Home Assistant มีขั้นต่ำของตัวเอง แต่ตัวเลขนั้นไม่ใช่ขนาดเครื่องที่รับประกันว่าสามารถรัน Frigate หลายกล้องได้ การใช้ทรัพยากรของ Frigate ขึ้นกับ:

  • จำนวนกล้อง
  • codec, resolution และ FPS ของ stream
  • จำนวน stream ที่ต้อง decode
  • scene activity และจำนวนวัตถุพร้อมกัน
  • detector/model และ input size
  • ระยะเวลาเก็บวิดีโอ
  • semantic search, LPR, GenAI หรือ enrichment อื่น

โปรไฟล์เริ่มต้นสำหรับการวางแผน (ไม่ใช่ minimum อย่างเป็นทางการ)

โปรไฟล์ งาน แนวทางฮาร์ดแวร์
ทดลอง 1 กล้อง, detect ต่ำ, retention สั้น x86-64 4 คอร์, RAM 8 GB, SSD; ใช้ OpenVINO CPU/GPU ได้ตามฮาร์ดแวร์
บ้านขนาดเล็ก 2–4 กล้อง 1080p/4MP, detect substream, record main stream CPU Intel/AMD รุ่นใหม่, RAM 16 GB, iGPU/GPU ที่ decode codec ได้, SSD ระบบ + storage แยก
ระบบจริงหลายกล้อง 5–12+ กล้อง, retention หลายวัน, enrichment RAM 16–32 GB+, accelerator ที่รองรับ, hardware decode, storage คำนวณจาก bitrate จริง, NIC และ UPS ที่เหมาะสม

ตัวเลขด้านบนเป็นจุดเริ่มต้นเผื่อทรัพยากร ไม่ใช่คำรับรอง ต้องพิสูจน์ด้วย System → Metrics → Cameras, detector latency, skipped detections, CPU/GPU load และ storage growth ของระบบจริง

สูตรประมาณพื้นที่เก็บวิดีโอ

พื้นที่ต่อวัน (GB) ≈ bitrate รวม (Mbps) × 10.8

ตัวอย่าง: 4 กล้อง กล้องละ 2 Mbps → 8 Mbps รวม → ประมาณ 86.4 GB/วัน ก่อนเผื่อ filesystem, metadata และ variation ของ VBR

AI Agent ต้องอ่าน bitrate จริงจาก stream probe หรือวัดการเติบโต 24–72 ชั่วโมง แล้วคำนวณ retention ใหม่ ห้ามใช้ตัวอย่างเป็นค่าจริง

การแยกเครื่อง

  • Home Assistant Container + Frigate Docker ใน host เดียว: เหมาะกับผู้ดูแล Linux/Docker ที่เข้าใจ device passthrough, backup และ resource isolation
  • Frigate App บน Home Assistant OS: สะดวกแต่ต้องตรวจการรองรับ accelerator/storage/passthrough ของรุ่นปัจจุบัน

CHAPTER 03

บทที่ 3 — Network และ Security Design

3.1 หลักการ

  • ให้ Home Assistant, Frigate และ MQTT มี IP คงที่ผ่าน DHCP reservation หรือ static address ที่ไม่ชน DHCP pool
  • ใช้ Ethernet สำหรับ server และกล้องที่รองรับ
  • หากทำ VLAN กล้อง ให้ Frigate เข้าถึงกล้องได้เฉพาะพอร์ตที่จำเป็น แต่ไม่ให้กล้องเริ่มการเชื่อมต่อเข้าวงผู้ใช้
  • จำกัดอินเทอร์เน็ตของกล้องเมื่อฟังก์ชันที่เลือกไม่ต้องใช้ cloud
  • ใช้ NTP/DNS ที่เชื่อถือได้ เพราะเวลาไม่ตรงทำให้ correlation และ recording ผิด
  • ใช้ VPN สำหรับ remote access เป็นค่าเริ่มต้น หลีกเลี่ยงการ forward RTSP/ONVIF หรือ NVR ออกอินเทอร์เน็ต

3.2 พอร์ตสำคัญที่ต้องจำกัด

  • Tapo RTSP: โดยทั่วไป 554
  • Tapo ONVIF: โดยทั่วไป 2020
  • Frigate authenticated UI/API: 8971
  • Frigate internal unauthenticated UI/API: 5000 — ห้ามเปิดสาธารณะ
  • go2rtc RTSP restream: 8554 — จำกัด trusted network หรือเปิด authentication
  • WebRTC: 8555 เมื่อจำเป็น
  • MQTT: ตาม broker/TLS ที่ตั้งไว้

3.3 Credential rules

  • ใช้ Camera Account แยกจากบัญชี cloud
  • ใช้ username/password ไม่ซ้ำกันในแต่ละระบบ
  • เก็บ secret ในไฟล์ environment/secret store ที่ permission จำกัด
  • ห้ามเขียน URL แบบ rtsp://user:password@... ใน Git หรือเอกสารสาธารณะ
  • ห้ามนำ port 5000 ผ่าน public reverse proxy
  • เปลี่ยนรหัส admin ที่ Frigate สร้างครั้งแรกทันที
CHAPTER 04

บทที่ 4 — ติดตั้ง Home Assistant

4.1 วิธีแนะนำสำหรับผู้เริ่มต้น: Home Assistant OS

  1. เลือกอุปกรณ์ที่หน้า Installation ทางการรองรับ
  2. ติดตั้ง HA OS ตามคู่มือของอุปกรณ์นั้น
  3. เชื่อม Ethernet และเปิดเครื่อง
  4. เปิดหน้า onboarding ผ่าน hostname หรือ IP ที่ router แสดง
  5. ตั้ง timezone, location และบัญชีผู้ดูแล
  6. ตั้ง backup schedule และดาวน์โหลด backup ทดลองหนึ่งชุด
  7. อัปเดต HA OS/Core/Apps ตาม release notes หลังสำรองข้อมูล

4.2 Home Assistant Container

เลือกวิธีนี้เมื่อมีผู้ดูแล Linux/Docker เพราะต้องดูแล OS, Docker, MQTT, backup, network และ update เอง Container ไม่มี Home Assistant Apps

AI Agent ต้อง:

  • pin หรือบันทึก image version ที่ deploy
  • mount /config ไป storage ถาวร
  • ตั้ง timezone
  • ใช้ restart policy
  • ทดสอบ restore จาก backup
  • ไม่ใช้ตัวอย่าง latest ใน production โดยไม่มีนโยบาย update/rollback

4.3 Acceptance criteria

  • UI ใช้งานได้จาก LAN
  • timezone ถูกต้อง
  • reboot แล้ว service กลับมาเอง
  • backup สร้างและ restore ใน sandbox ได้
  • mobile app เชื่อมต่อและสร้าง notify.mobile_app_<device_id> ได้
CHAPTER 05

บทที่ 5 — MQTT Broker

MQTT เป็น optional สำหรับ Frigate แบบ standalone แต่จำเป็นสำหรับ Frigate Integration ใน Home Assistant และ entity/event หลายรายการ

5.1 HA OS

  • ใช้ Mosquitto Broker App ตามเอกสาร Home Assistant
  • สร้างผู้ใช้เฉพาะสำหรับ Frigate หรือใช้ credential ที่ integration สร้างอย่างปลอดภัย

5.2 Container

  • รัน broker แยก
  • เปิด authentication
  • ใช้ TLS เมื่อข้าม trusted network
  • ไม่ใช้ public MQTT broker สำหรับข้อมูลกล้อง

5.3 ตรวจสอบ

  • Home Assistant MQTT Integration แสดง connected
  • Frigate กับ Home Assistant ชี้ broker เดียวกัน
  • ถ้ามีหลาย Frigate instance ให้ topic_prefix และ client_id ไม่ซ้ำ
  • ตรวจ frigate/available, frigate/reviews, frigate/events และ frigate/stats
CHAPTER 06

บทที่ 6 — ติดตั้ง Frigate

6.1 แนวทาง deployment

Frigate เป็น Docker container และเอกสารแนะนำ Docker Compose บน Debian-based host สำหรับการเข้าถึง GPU/accelerator โดยตรงและมี overhead ต่ำ

ก่อนสร้าง Compose ให้ AI Agent ตรวจ:

  • CPU architecture และ AVX/AVX2 ตามข้อกำหนดรุ่นปัจจุบัน
  • /dev/dri หรือ device ของ accelerator
  • codec ที่ GPU decode ได้
  • storage mount และ free space
  • timezone
  • Docker/Compose version
  • เจ้าของและ permission ของ config/storage

6.2 โครง Compose แบบสาธารณะ

ต้องนำไปเทียบกับ Compose ตัวอย่างทางการของ Frigate รุ่นที่จะติดตั้ง ห้ามคัดลอกไป production โดยไม่แก้ placeholder

services:
  frigate:
    container_name: frigate
    image: ghcr.io/blakeblackshear/frigate:<PINNED_VERSION>
    restart: unless-stopped
    shm_size: "<CALCULATED_SIZE>"
    devices:
      - source: <HOST_ACCELERATOR_DEVICE>
        target: <CONTAINER_ACCELERATOR_DEVICE>
        permissions: rwm
    volumes:
      - type: bind
        source: <CONFIG_DIRECTORY>
        target: /config
      - type: bind
        source: <MEDIA_DIRECTORY>
        target: /media/frigate
    ports:
      - "<TRUSTED_BIND_IP>:8971:8971"
      - "<TRUSTED_BIND_IP>:8554:8554"
      - "<TRUSTED_BIND_IP>:8555:8555/tcp"
      - "<TRUSTED_BIND_IP>:8555:8555/udp"
    environment:
      FRIGATE_CAMERA_PASSWORD: "${FRIGATE_CAMERA_PASSWORD}"

อย่า publish port 5000 ไปยัง network ที่ไม่ไว้ใจ และไม่ต้อง publish 8555 หากไม่ได้ใช้ WebRTC/two-way audio หากต้องใช้ให้จำกัด interface, firewall หรือ VPN ตาม threat model

6.3 Detector

  • ใช้ GPU/NPU/accelerator ที่เอกสารรองรับเมื่อเป็นไปได้
  • OpenVINO เหมาะกับ Intel CPU/iGPU/GPU/NPU ที่รองรับ และอาจทำงาน CPU บางแพลตฟอร์ม
  • CPU detector ของ TensorFlow Lite เหมาะสำหรับทดลอง/ฉุกเฉิน ไม่แนะนำระบบจริงทั่วไป
  • Coral ยังรองรับแต่เอกสารปัจจุบันไม่แนะนำเป็นตัวเลือกใหม่สำหรับระบบส่วนใหญ่ ยกเว้นกรณีพลังงานต่ำหรือข้อจำกัดฮาร์ดแวร์
  • ห้ามผสม detector backend ต่างชนิดเพื่อ object detection หากรุ่นปัจจุบันไม่รองรับ
  • เริ่ม model input 320×320 ตามคำแนะนำทั่วไป แล้ววัด skipped detections ก่อนเพิ่มขนาด/variant

6.4 Hardware video decoding

Video decoding กับ object detection เป็นคนละงาน ต้องเปิด FFmpeg hardware acceleration ให้ตรง GPU และตรวจ log ว่าไม่มี error Frigate ไม่มี CPU fallback อัตโนมัติเมื่อกำหนด hardware acceleration แล้วแต่ใช้งานไม่ได้

Substream:   rtsp://<CAMERA_USER>:<CAMERA_PASSWORD>@<CAMERA_IP>:554/stream2

7.2 ใช้ go2rtc ลด connection

go2rtc:
  streams:
    front_entry_main:
      - "rtsp://<CAMERA_USER>:{FRIGATE_CAMERA_PASSWORD}@<CAMERA_IP>:554/stream1"
    front_entry_sub:
      - "rtsp://<CAMERA_USER>:{FRIGATE_CAMERA_PASSWORD}@<CAMERA_IP>:554/stream2"

go2rtc ช่วยให้ Frigate, live view และ Home Assistant แชร์ connection โดยไม่ re-encode ในกรณีที่ codec/client รองรับ ตรวจสถานะที่ /api/go2rtc/streams

7.3 Stream roles

  • detect: ใช้ substream ที่ความละเอียด/FPS ต่ำพอและเห็นวัตถุชัด
  • record: ใช้ main stream คุณภาพสูง
  • audio: ใช้เฉพาะเมื่อเปิด audio detection

แต่ละ role กำหนดได้ครั้งเดียวต่อกล้อง

cameras:
  front_entry:
    ffmpeg:
      inputs:
        - path: rtsp://127.0.0.1:8554/front_entry_sub
          roles: [detect]
        - path: rtsp://127.0.0.1:8554/front_entry_main
          roles: [record]
    detect:
      enabled: true
      width: <SUBSTREAM_WIDTH>
      height: <SUBSTREAM_HEIGHT>
      fps: <MEASURED_TARGET_FPS>

ค่าความกว้าง/สูงต้องตรง stream probe ห้ามเดา

CHAPTER 08

บทที่ 8 — Object Detection, Filters, Zone และ Mask

8.1 Labels

Frigate ติดตาม person เป็นค่าเริ่มต้น หากต้องการรถต้องเพิ่ม label:

objects:
  track:
    - person
    - car
    - motorcycle

การใส่ label ใน review/alert ไม่ได้ทำให้ detector เริ่มติดตาม label นั้น ต้องอยู่ใน objects.track

8.2 Object filters

ปรับต่อกล้องจากข้อมูลจริง:

  • min_area/max_area: ขนาด bounding box
  • min_ratio/max_ratio: อัตราส่วนกว้างต่อสูง
  • min_score: คะแนนเริ่มติดตาม
  • threshold: คะแนนยืนยัน true positive

อย่าคัดลอก filter ข้ามกล้อง เพราะ perspective ต่างกัน

8.3 Zone กับ Mask ต่างกันอย่างไร

  • Zone + required_zones: ใช้เมื่ออยากแจ้งเฉพาะพื้นที่สำคัญ
  • Motion mask: กัน motion ที่ไม่จำเป็น เช่น timestamp/กิ่งไม้ ไม่ได้ซ่อนวัตถุ
  • Object filter mask: กรอง false positive ของ label ที่ตำแหน่งคงที่ซึ่งเป็นไปไม่ได้
  • Mask ไม่ใช่ privacy redaction และไม่หยุด continuous recording นอกพื้นที่

Zone พิจารณาจาก จุดกึ่งกลางด้านล่างของ bounding box ไม่ใช่พื้นที่ overlap ทั้งกล่อง

8.4 วิธีวาด Polygon จากภาพจริง

  1. เปิดภาพล่าสุดจากกล้องใน Frigate UI
  2. ไปที่ Settings → Camera configuration → Masks / Zones
  3. เพิ่ม Zone และคลิกจุดตามขอบพื้นที่จริง
  4. ปิด polygon ด้วยจุดแรก
  5. ตั้งชื่อแบบ stable ID เช่น entry_threshold หรือ driveway_inner
  6. เลือก object ที่อนุญาต
  7. บันทึกและเปิด Debug View พร้อม Zones/Object Boxes
  8. เดิน/ขับผ่านเส้นจริงหลายตำแหน่ง
  9. ตรวจจุด bottom-center ของ bounding box ว่าเข้า Zone ในจังหวะที่ต้องการ
  10. เก็บ snapshot ที่ใช้อนุมัติ geometry และบันทึกเหตุผลของแต่ละจุด

ตัวอย่างพิกัด normalized:

zones:
  entry_threshold:
    coordinates: 0.18,0.82,0.36,0.54,0.71,0.55,0.91,0.84
    objects:
      - person

ตัวเลขตัวอย่างนี้ห้ามใช้กับกล้องจริง ต้องสร้างจากภาพกล้องจริง

8.5 Alert เฉพาะ Zone

review:
  alerts:
    required_zones:
      - entry_threshold

ตรวจ syntax กับ documentation ของ Frigate รุ่นปัจจุบันก่อน deploy

บทที่ 9 — กรณีคนที่หน้าประตู

9.1 Logic ที่แนะนำ

person tracked
  AND bottom-center enters entry_threshold
  AND confidence/filter passes
  AND cooldown/dedup permits
→ create/retrieve exact review or event
→ send snapshot + text
→ optional Android TTS

9.2 ป้องกัน false alert

  • อย่าวาด Zone ครอบถนน/ทางเท้าสาธารณะหากไม่ต้องการแจ้ง
  • ใช้ loitering เมื่อไม่ต้องการแจ้งคนเดินผ่านเร็ว
  • ปรับ object filter จากตัวอย่าง true/false positives
  • ทดสอบกลางวัน กลางคืน ฝน และย้อนแสง
  • อย่าใช้ mask กว้างจน tracking ขาด

9.3 Acceptance tests

  • คนยืนหน้าประตู → แจ้งหนึ่งครั้งพร้อมภาพถูก event
  • คนเดินนอก Zone → ไม่มี alert
  • คนเข้า Zone แล้วอยู่นาน → ไม่ spam
  • คนออกแล้วกลับเข้าหลัง cooldown → เกิดเหตุใหม่ตามนโยบาย
  • โทรศัพท์ offline → ข้อความส่งเมื่อกลับ online ตามข้อจำกัด push; event ไม่สูญหายหากออกแบบ queue
CHAPTER 10

บทที่ 10 — รถเข้าและรถออก

10.1 กล้องหนึ่งตัว

ใช้ Zone ตามลำดับ เช่น:

road_edge → driveway_outer → driveway_inner
  • เข้า: พบ road_edge แล้ว driveway_outer แล้ว driveway_inner
  • ออก: ลำดับย้อนกลับ

ข้อจำกัด:

  • object อาจหายจาก tracking เมื่อถูกบัง
  • event ID อาจเปลี่ยนหาก tracking ขาด
  • เวลาใกล้กันอย่างเดียวไม่พิสูจน์ว่าเป็นรถคันเดียวกัน
  • ภาพมุมเดียวอาจอ่านทะเบียน/ยี่ห้อไม่ได้

ให้ระบบรายงาน “ทิศทางที่สันนิษฐานจากลำดับ Zone” พร้อม confidence แทนการยืนยันแบบเด็ดขาด

10.2 สองกล้อง

การวางที่มีประโยชน์:

  • กล้อง A มุมกว้าง เห็นเส้นทางและทิศทาง
  • กล้อง B มุมแคบ/สูงพอเหมาะ เก็บด้านหน้า/ท้ายรถหรือทะเบียน

ประโยชน์:

  • ลดมุมอับและการบดบัง
  • มีหลักฐานอีกมุม
  • ช่วยยืนยันลำดับเข้า/ออก
  • เพิ่มโอกาสได้ crop คุณภาพดีสำหรับ OCR/MMC

ต้นทุน:

  • bandwidth, decode, storage และ inference เพิ่ม
  • geometry และ time synchronization ซับซ้อนขึ้น
  • การพบเหตุสองกล้องไม่พิสูจน์ว่าเป็นรถคันเดียวกัน

10.3 Correlation ที่ปลอดภัย

เก็บต่อเหตุการณ์:

observation:
  camera_id: "<CAMERA_ID>"
  event_or_review_id: "<EXACT_ID>"
  object_label: "car"
  zones_entered: ["<ZONE_ID>"]
  start_time: "<UTC_TIMESTAMP>"
  end_time: "<UTC_TIMESTAMP>"
  plate_text: "<VALUE_OR_UNKNOWN>"
  plate_confidence: <NUMBER_OR_NULL>
  visual_embedding_id: "<OPTIONAL_REFERENCE>"

Correlation ใช้หลายสัญญาณร่วมกัน เช่น exact IDs, Zone sequence, direction, plate confidence และภาพ ไม่ใช้ timestamp อย่างเดียว หากหลักฐานไม่พอให้สร้าง observations แยกกัน

บทที่ 11 — ประเภทรถ สี ยี่ห้อ รุ่น และทะเบียน

11.1 สิ่งที่ detector ปกติทำได้

Frigate object detector ปกติใช้ class กว้าง เช่น:

  • car
  • motorcycle
  • bus
  • label อื่นตาม model ที่เลือก

นี่ไม่เท่ากับการรู้ยี่ห้อ รุ่น ปี หรือเจ้าของรถ

11.2 License Plate Recognition

Frigate รุ่นปัจจุบันมี LPR enrichment ตามเอกสาร ต้อง:

  • มีภาพทะเบียนใหญ่และชัดพอ
  • เลือกกล้อง/mode ที่เหมาะ
  • เปิด feature และดาวน์โหลด model ตามข้อกำหนด
  • กำหนด threshold และ format validation ตามประเทศ
  • เก็บ unknown เมื่ออ่านไม่ได้
  • ไม่ใช้ทะเบียนเพียงอย่างเดียวในการตัดสินความปลอดภัย

11.3 Vehicle type/make/model/color

แนวทาง:

  1. Frigate ตรวจ car
  2. ดึง crop/snapshot จาก exact event ID
  3. ตรวจคุณภาพภาพ: ขนาดรถ, blur, แสง, occlusion
  4. ส่งไป secondary classifier/MMC service หรือ local vision model
  5. รับผลพร้อม confidence
  6. ใช้ threshold แยก known/unknown
  7. บันทึก model version และ source image ID
  8. ให้มนุษย์ตรวจเมื่อมีผลกระทบสำคัญ

สิ่งที่ห้ามทำ

  • เปลี่ยนชื่อ label map แล้วอ้างว่า model รู้ class ใหม่
  • ใช้ Semantic Search เป็น deterministic classifier
  • ให้ Vision LLM เดายี่ห้อ/รุ่นแล้วประกาศเป็นข้อเท็จจริง
  • ส่งภาพส่วนตัวไป cloud model โดยไม่แจ้งและไม่ได้รับความยินยอม

รูปแบบผลลัพธ์

{
  "vehicle_type": {"value": "suv", "confidence": 0.82},
  "color": {"value": "white", "confidence": 0.71},
  "make": {"value": "unknown", "confidence": null},
  "model": {"value": "unknown", "confidence": null},
  "plate": {"value": "unknown", "confidence": null},
  "source_event_id": "<EXACT_EVENT_ID>",
  "model_version": "<MODEL_VERSION>"
}

หาก Vision LLM ใช้สร้างข้อความ ควรเขียนว่า “น่าจะเป็นรถ SUV สีอ่อน; ไม่สามารถยืนยันยี่ห้อหรือรุ่นได้”

บทที่ 13 — Android Notification และเสียง TTS

13.1 ข้อความพร้อมภาพ

- action: notify.mobile_app_<ANDROID_DEVICE_ID>
  data:
    title: "ตรวจพบวัตถุ"
    message: "ตรวจพบ {{ object_label }} ในพื้นที่ {{ zone_name }}"
    data:
      image: "<VERIFIED_IMAGE_SOURCE>"
      tag: "frigate-{{ exact_event_id }}"
      clickAction: "/dashboard/cameras"
      channel: "Camera alerts"
  • payload ต้องมี message
  • URL/แหล่งภาพต้องเข้าถึงได้จากโทรศัพท์
  • ทางเลือกที่หนึ่งคือใช้ media_source หรือกลไก Home Assistant ที่ส่ง authentication header ซึ่งต้องทดสอบจากโทรศัพท์จริง
  • ทางเลือกที่สองคือ Frigate Integration notification endpoint เช่น /api/frigate/notifications/<event-id>/snapshot.jpg ซึ่งเอกสารระบุว่าเป็น public notification endpoint จึงต้องประเมินการเปิดเผย URL/ภาพและเส้นทาง external access ก่อนใช้ ห้ามเรียกว่า authenticated endpoint
  • ใช้ tag จาก exact ID เพื่อ deduplicate/update

13.2 TTS บน Android

- action: notify.mobile_app_<ANDROID_DEVICE_ID>
  data:
    message: "TTS"
    data:
      tts_text: "ตรวจพบคนในพื้นที่ทางเข้า"
      ttl: 0
      priority: high
      media_stream: "alarm_stream"

ข้อจำกัด:

  • TTS รองรับ locale ตาม TTS engine ของ Android
  • ค่าเริ่มต้นมักใช้ music stream; alarm_stream ใช้เสียง alarm
  • alarm_stream_max ดังสุดชั่วคราว ควรใช้เฉพาะเหตุฉุกเฉิน
  • ttl: 0 + priority: high ช่วยความเร่งด่วน แต่ไม่ข้าม Do Not Disturb อัตโนมัติ
  • Notification channel, permission, DND, battery optimization, vendor firmware, network และ volume มีผล
  • channel settings บน Android 8+ อาจถูกล็อกตามค่าที่สร้างครั้งแรกหรือค่าที่ผู้ใช้แก้
  • ตรวจ call state/DND/ringer/audio ก่อนพูดเพื่อลดการรบกวน
  • Companion App ไม่ได้เปลี่ยน TTS ที่ล้มเหลวเป็นข้อความให้อัตโนมัติ จึงต้องส่ง normal notification พร้อมข้อความ/ภาพเป็น action แยก หรือใช้ automation choose เป็น fallback
  • ใช้ command_stop_tts ตามเอกสารเมื่อจำเป็นต้องหยุดเสียง

13.3 Quiet hours

condition:
  - condition: time
    after: "<QUIET_HOURS_END>"
    before: "<QUIET_HOURS_START>"

หรือแยก policy:

  • เหตุทั่วไป: ข้อความ/ภาพอย่างเดียวใน quiet hours
  • เหตุสำคัญ: TTS เฉพาะอุปกรณ์ที่ opt-in
  • เหตุฉุกเฉิน: critical channel ตามสิทธิ์และนโยบายที่มนุษย์อนุมัติ

บทที่ 14 — Durable Event Handling และการไม่แจ้งซ้ำ

ระบบที่เชื่อถือได้ควรมี:

  • exact event/review ID เป็น idempotency key
  • durable queue/outbox สำหรับ notification สำคัญ
  • retry แบบ exponential backoff
  • dead-letter/error log ที่ไม่มี secret
  • state received → enriched → notified → acknowledged/failed
  • cooldown ต่อ camera/zone/object
  • max age เพื่อไม่อ่านเสียงเหตุการณ์เก่าหลัง service กลับมา
  • แยก notification channel สำหรับข้อความกับเสียง

หากส่งภาพสำเร็จแต่ TTS ล้มเหลว ให้ถือว่า notification แบบข้อความยังสำเร็จบางส่วนและบันทึกสถานะแยก ห้ามส่งภาพซ้ำอย่างไม่จำกัด

CHAPTER 15

บทที่ 15 — Recording, Snapshot และ Retention

  • Snapshot กับ recording เป็นคนละ feature ต้องเปิดและทดสอบแยก
  • Snapshot เป็น best frame ของ tracked object
  • Recording คัดลอก stream โดยไม่ re-encode เมื่อ codec/container รองรับ
  • ตั้ง retention สำหรับ continuous, motion, alerts และ detections อย่างชัดเจน
  • required_zones จำกัด review item ไม่ได้แทน recording policy
  • Export หลักฐานที่ต้องเก็บยาว เพราะ export แยกจาก normal retention
  • จำกัดสิทธิ์เข้าถึง media และ backup
  • กำหนดนโยบายลบข้อมูล/ความยินยอมตามกฎหมายพื้นที่ติดตั้ง

การทดสอบ retention

  1. สร้างเหตุการณ์ควบคุม
  2. ตรวจ snapshot
  3. เล่นคลิปก่อน/ระหว่าง/หลังเหตุการณ์
  4. ตรวจ pre/post capture
  5. ตรวจการลบเมื่อครบ retention ใน staging
  6. ตรวจ free-space monitoring และพฤติกรรมเมื่อดิสก์ใกล้เต็ม
CHAPTER 16

บทที่ 16 — Test Plan และ Acceptance Criteria

16.1 Infrastructure

  • ทุก service กลับมาหลัง reboot
  • ไม่มี restart loop
  • เวลา/NTP ตรงกัน
  • backup และ rollback ทดสอบได้
  • ไม่มี secret ใน repository/log/public artifact
  • พอร์ต unauthenticated ไม่เปิดสู่อินเทอร์เน็ต

16.2 Camera/stream

  • main/substream probe ผ่านและค่าตรง config
  • live view เปิดจาก client จริง
  • ไม่มี FFmpeg/watchdog restart ซ้ำ
  • go2rtc debug แสดง consumer/producer ปกติ
  • camera connection ไม่เกินข้อจำกัดรุ่น

16.3 Detection

  • person ใน Zone → alert
  • person นอก Zone → no alert
  • car เข้า → direction hypothesis ถูกตาม Zone sequence
  • car ออก → direction hypothesis ถูกตาม Zone sequence
  • motorcycle ทดสอบแยก
  • false-positive fixtures ไม่สร้าง alert
  • กลางวัน/กลางคืน/ฝน/ย้อนแสงผ่านเกณฑ์ที่กำหนด

16.4 Performance

  • ไม่มี skipped detections ที่ยอมรับไม่ได้
  • detector latency/load อยู่ในงบ
  • CPU/GPU/VRAM/RAM มี headroom
  • storage growth ตรงประมาณการหลังวัดจริง
  • เพิ่มกล้องทีละตัวและทดสอบซ้ำ

16.5 Home Assistant/Android

  • MQTT reconnect หลัง broker restart
  • Integration entities available
  • notification ใช้ exact event image
  • tag deduplicate ได้
  • Android online/offline behavior ผ่าน
  • TTS ภาษา/volume/channel ถูกต้อง
  • DND และ quiet-hours policy ทำงาน
  • ข้อความ fallback ยังมาถึงเมื่อ TTS ไม่ทำงาน

16.6 รถและ enrichment

  • OCR มี confidence และ unknown
  • make/model ไม่ยืนยันเมื่อภาพไม่พอ
  • cloud processing ได้รับ consent
  • model version และ source event ID ถูกบันทึก
  • ไม่มี high-risk automation ที่เชื่อผล Vision LLM เพียงอย่างเดียว
CHAPTER 17

บทที่ 17 — Rollback Plan

ก่อนเปลี่ยนแต่ละครั้ง:

  1. export config และบันทึก container image/version
  2. สำรอง Home Assistant
  3. สำรอง Frigate config/database ตามเอกสารรุ่นนั้น
  4. บันทึก baseline health, ports, storage และ MQTT topics
  5. เปลี่ยนทีละส่วน

Rollback เมื่อ:

  • camera stream ไม่เสถียร
  • detector/FFmpeg restart loop
  • CPU/GPU/storage สูงผิดปกติ
  • alert หายหรือ spam
  • notification routing ผิดอุปกรณ์
  • เกิด exposure ของ port/credential

วิธีทั่วไป:

stop changed service
restore previous config
restore previous image tag
start service
verify logs, health, stream, MQTT, notification

หาก credential รั่ว ต้อง rotate credential ไม่ใช่แค่ลบออกจาก Git history

CHAPTER 18

บทที่ 18 — Troubleshooting

กล้องเปิดในแอปได้ แต่ Frigate เปิดไม่ได้

  • ยืนยันว่ารุ่นรองรับ RTSP/ONVIF
  • ใช้ Camera Account ไม่ใช่ cloud account
  • ตรวจ DHCP reservation/IP
  • ตรวจ stream path stream1/stream2
  • ตรวจจำนวน local viewers
  • ปิด VLC/NVR client ชั่วคราว
  • ตรวจ VLAN/firewall และ DNS/NTP
  • ทดสอบจาก host เดียวกับ Frigate

FFmpeg restart ซ้ำ

  • probe codec/resolution/FPS
  • ตรวจ credential โดยไม่พิมพ์ลง log
  • ตรวจ hardware acceleration preset/device mapping
  • ตรวจ camera connection limit
  • ตรวจ packet loss/PoE/Wi‑Fi
  • ใช้ substream สำหรับ detect

ตรวจพบแต่ไม่เกิด alert

  • label อยู่ใน objects.track หรือไม่
  • score/filter ผ่านหรือไม่
  • bottom-center เข้า Zone หรือไม่
  • required_zones ใช้ชื่อถูกต้องหรือไม่
  • review severity/retention config ถูกหรือไม่
  • ดู Debug View ไม่เดาจากภาพนิ่งอย่างเดียว

Alert มากเกินไป

  • ลด Zone ให้ตรงพื้นที่
  • เพิ่ม loitering/inertia ตามกรณี
  • ปรับ filter จาก false positives จริง
  • ใช้ cooldown/dedup
  • อย่าแก้ด้วย motion mask ขนาดใหญ่โดยไม่ทดสอบ tracking

Android ไม่พูด

  • ตรวจ notification permission และ target device ID
  • ตรวจ TTS engine/locale
  • ตรวจ volume, channel, DND และ battery optimization
  • ทดสอบข้อความธรรมดาก่อน แล้วค่อย TTS
  • ทดสอบ music_stream/alarm_stream ตามนโยบาย
  • ตรวจว่าโทรศัพท์เข้าถึง Home Assistant ได้
  • คงข้อความ fallback

อ่านยี่ห้อรถผิด

  • เพิ่ม pixel density ของรถ/crop
  • ลด motion blur และย้อนแสงด้วยตำแหน่ง/ชัตเตอร์ที่เหมาะ
  • ใช้ classifier ที่ฝึกตรงโจทย์
  • calibrate threshold ด้วย test set จากกล้องจริง
  • คืนค่า unknown เมื่อ confidence ต่ำ
  • ห้ามแก้ด้วย prompt ที่บังคับให้ตอบยี่ห้อ
CHAPTER 19

บทที่ 19 — Runbook สำหรับ AI Agent แบบเป็นลำดับ

Phase A: Discovery (read-only)

  1. เก็บ inventory โดยไม่เก็บ secret
  2. ตรวจ compatibility จาก official docs
  3. วัด network/storage/codec
  4. เลือก architecture และ threat model
  5. สร้าง acceptance criteria และ rollback
  6. ให้มนุษย์อนุมัติขอบเขตที่มี side effect

Phase B: Minimum Viable System

  1. ติดตั้ง Home Assistant
  2. ติดตั้ง MQTT
  3. ติดตั้ง Frigate ด้วย detector/hwaccel
  4. เพิ่มกล้องหนึ่งตัว
  5. ยืนยัน stream, metrics, recording
  6. วาด Zone จากภาพจริง
  7. ทดสอบ person
  8. เชื่อม Frigate Integration
  9. ส่ง Android text + image
  10. เปิด TTS หลังข้อความผ่าน

Phase C: Vehicle Workflow

  1. เพิ่ม car/motorcycle
  2. สร้าง Zone sequence
  3. ทดสอบเข้า/ออกหลายรอบ
  4. เก็บ exact IDs และ confidence
  5. เพิ่มกล้องสองเมื่อมีมุมอับหรือจำเป็นต้องเก็บทะเบียน
  6. เพิ่ม LPR/MMC เป็น enrichment แยก
  7. ทดสอบ unknown และ failure modes

Phase D: Hardening

  1. แยก VLAN/firewall
  2. ปิด public exposure
  3. rotate/default credentials
  4. ตั้ง backup/retention/monitoring
  5. ทดสอบ reboot, network loss, broker loss, disk pressure
  6. ทำ privacy review
  7. สร้างเอกสารส่งมอบและแผนบำรุงรักษา

Definition of Done

AI Agent ห้ามรายงานว่า “เสร็จ” จนกว่า:

  • ทุก acceptance test มีผลจริง
  • มีหลักฐานจาก log/state/output ไม่ใช่เพียง config valid
  • notification ถูกส่งไปอุปกรณ์ทดสอบจริง
  • snapshot/clip เปิดได้
  • rollback ผ่านหรือมีเหตุผลที่ตรวจไม่ได้
  • ไม่มี secret/ข้อมูลบ้านใน artifact สาธารณะ
  • มีรายการ version, assumptions, limitations และงานค้าง
