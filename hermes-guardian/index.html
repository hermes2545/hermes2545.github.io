Monitor → Operator Profile Playbook
✨ Public-safe architecture guide

ระบบเฝ้าดูอัตโนมัติที่ส่งต่อให้โปรไฟล์หลักตรวจและซ่อมอย่างปลอดภัย

แนวทางนี้แยกบทบาทเป็นโปรไฟล์เฝ้าระวังและโปรไฟล์ปฏิบัติการ เพื่อให้การตรวจ error เป็นแบบอ่านอย่างเดียวก่อน แล้วจึงส่งต่องานให้โปรไฟล์ที่มีสิทธิ์ลงมือ พร้อมแจ้งผู้ดูแลเป็นภาษาคนทุกจังหวะ

Read-only firstผู้เฝ้าดูไม่แก้ระบบเอง
Human noticeแจ้งเหตุ ส่งต่อ และผลซ่อม
Bounded repairซ่อมเฉพาะจุดพร้อม verify

แนวคิดหลัก

ออกแบบให้แยก “คนเฝ้า” ออกจาก “คนลงมือ” เพื่อลดความเสี่ยงจาก automation ที่แก้ระบบเองโดยไม่ตรวจหลักฐาน

👁️

โปรไฟล์เฝ้าระวัง

ทำหน้าที่ตรวจสถานะ อ่าน log สรุปความผิดปกติ เก็บสถานะการแจ้งซ้ำ และแจ้งผู้ดูแลโดยไม่แตะระบบเป้าหมาย

🧠

โปรไฟล์คัดกรอง

แปล alert เชิงเทคนิคให้เป็นภาษาคน ประเมินผลกระทบและความเร่งด่วน ก่อนตัดสินใจว่าจะส่งต่อหรือไม่

🛠️

โปรไฟล์ปฏิบัติการ

รับงานแบบมีขอบเขต ตรวจหลักฐานจริง แก้เฉพาะจุดที่ปลอดภัย และยืนยันผลด้วยการทดสอบจริง

หลักการสำคัญ: alert ไม่ควรเป็นแค่คำว่า error แต่ต้องบอกว่าคนดูแลควรรู้อะไร ผลกระทบคืออะไร ส่งให้ใครทำต่อ และจบด้วยสถานะอะไร
Monitor Profile
  • อ่านสถานะบริการ งาน scheduled task และผลการรันล่าสุด
  • ตรวจเฉพาะข้อมูลที่จำเป็นต่อการแจ้งเตือน
  • ทำ dedupe เพื่อไม่ส่ง alert เดิมซ้ำเกินจำเป็น
  • ส่งข้อความภาษาคนให้ผู้ดูแลทราบ
  • ไม่แก้ config ไม่ restart และไม่ใช้ credential ของโปรไฟล์หลัก
Operator Profile
  • รับ prompt ส่งต่อพร้อมบริบทที่ผ่านการย่อและ redaction
  • ตรวจหลักฐานจากแหล่งจริงก่อนสรุปสาเหตุ
  • แก้เฉพาะปัญหาที่อยู่ในขอบเขตปลอดภัย
  • หยุดเมื่อเจอ action ที่ต้องอนุมัติหรือแตะ credential
  • รายงานผลเป็นภาษาคนพร้อมหลักฐานการ verify
⏱️

Scheduled task health

ตรวจว่างานที่เปิดใช้งานมีสถานะล่าสุดเป็นปกติหรือไม่ มีงานค้าง งาน timeout งานไม่เคยรัน หรือรอบล่าสุดล้มเหลวหรือไม่

📦

Execution evidence

อ่านฐานข้อมูลผลการรันหรือไฟล์ output ล่าสุด เพื่อแยกว่าปัญหาเป็นแค่สถานะค้างหรือรันล้มเหลวจริง

📡

Delivery health

ตรวจว่าผลลัพธ์ส่งออกไปยังช่องทางแจ้งเตือนได้หรือไม่ และแยกปัญหาช่องทางส่งออกออกจากปัญหาของงานหลัก

🧯

Service & resource signals

ตรวจสัญญาณระดับเครื่องหรือ service เช่น service หยุด พื้นที่ดิสก์ใกล้เต็ม หรือ heartbeat หาย โดยจัดเป็นคนละชั้นกับ error ของงานย่อย

1
Watchโปรไฟล์เฝ้าระวังอ่านสถานะล่าสุดแบบ read-only
2
Classifyจัดประเภทความผิดปกติและคัด alert ที่ควรแจ้ง
3
Notifyแจ้งผู้ดูแลว่าเกิดอะไรขึ้นและจะส่งต่อหรือไม่
4
Escalateเปิด session แบบจำกัดสิทธิ์ให้โปรไฟล์ปฏิบัติการตรวจและซ่อม
5
Reportส่งผลกลับเป็นภาษาคน พร้อมสถานะหลัง verify
🛎️

แจ้งเมื่อพบปัญหา

บอกเรื่องที่ผิดปกติ ผลกระทบ ความเร่งด่วน และสิ่งที่โปรไฟล์เฝ้าระวังทำไปแล้ว โดยไม่ใส่ log ยาวในข้อความหลัก

📣

แจ้งเมื่อส่งต่อ

บอกชัดเจนว่าโปรไฟล์เฝ้าระวังส่งงานให้โปรไฟล์ปฏิบัติการแล้ว และโปรไฟล์ปฏิบัติการจะตรวจอะไรต่อ

✅

แจ้งเมื่อจบงาน

บอกว่าแก้สำเร็จหรือยังติด blocker สาเหตุคืออะไร ซ่อมอะไร ตรวจสอบผลอย่างไร และผู้ดูแลต้องทำอะไรต่อหรือไม่

🔒

Fail-safe boundary

โปรไฟล์เฝ้าระวังไม่ควรมีสิทธิ์แก้ระบบเป้าหมายโดยตรง การแก้ต้องผ่าน prompt ส่งต่อที่จำกัดสิทธิ์และมีเงื่อนไขหยุด

🧹

Sanitized context

ข้อความส่งต่อควรมีเฉพาะข้อมูลจำเป็น ไม่ใส่ token, secret, path ส่วนตัว, chat id, task id จริง หรือข้อมูลเฉพาะองค์กร

🧪

Verification required

ทุกการซ่อมต้องจบด้วยการตรวจจริง เช่น syntax check, import check, dry-run, scheduler run หรือ health check ตามชนิดของงาน

🛑

Stop conditions

ถ้าต้อง restart, ใช้เงิน, ลบข้อมูล, แตะ credential, เปลี่ยน security policy หรือเดา secret ต้องหยุดและขออนุมัติ

Mega Prompt สำหรับสร้างระบบนี้ในเครื่องอื่น

คัดลอกไปให้ Hermes Agent บนเครื่องปลายทาง ใช้ placeholder กลางและให้ตรวจ environment จริงก่อนลงมือ

Prompt นี้ไม่ผูกกับชื่อบุคคล องค์กร งาน หรือ path เฉพาะเครื่อง
เอกสารนี้ใช้คำกลางสำหรับแชร์สาธารณะ ไม่รวมชื่อบุคคล องค์กร งานภายใน token หรือ path เฉพาะเครื่อง
