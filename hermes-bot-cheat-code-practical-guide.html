Hermes Bot Cheat Code

สูตรโกงสร้างทีม AI ให้ทำงานแทนคุณ

ไม่ได้สอนแค่ “เปิด Bot ตรงไหน” แต่พาไล่ตั้งแต่สร้าง Bot → เขียน Soul → จำกัด Tools/MCP → เลือก Model → วาง Memory → ตั้ง Guardrails → ประกอบเป็นทีม → สอนทีมให้เรียนรู้จากงานที่จบ

อ่านเป็นบท ไม่ใช่ long scrollมี Prompt ทดลองทุกเทคนิคบันทึกความคืบหน้าในเครื่อง

แก่นของ Cheat Code

จุดปลดล็อกไม่ใช่ “มี Bot เยอะ” แต่คือการประสานงาน: แต่ละ Bot มีงานชัด ใช้เครื่องมือเท่าที่จำเป็น และส่งต่องานกันโดยที่คุณไม่ต้องเป็นคนวิ่งงานระหว่างแชตเอง

วิธีใช้คู่มือนี้

ทำทีละบทกับระบบจริงของคุณ อย่ากระโดดไปสร้างทีมใหญ่ทันที เริ่มหนึ่ง Bot → ทดสอบ → ล็อกบทบาท → ค่อยเพิ่ม Bot และการส่งต่องาน

เส้นทางการลงมือทำ
Bot→Soul→Tools / MCP→Model→Memory→Guardrails→Team→Learn
หมายเหตุเรื่อง Prompt: Prompt ตัวอย่างในคู่มือนี้เรียบเรียงขึ้นใหม่จากหลักการใน transcript เพื่อให้เอาไปทดลองได้ทันที ไม่ใช่การคัดลอก “exact prompts” จากบทความภายนอกที่ผู้พูดอ้างถึงแต่ไม่ได้อยู่ในไฟล์ต้นฉบับนี้

01
Foundation

เข้าใจ Bot Mode ก่อนสร้างทีม

ในต้นฉบับ Bot ถูกอธิบายตรง ๆ ว่าเป็น Profile ที่มี persona, model, tools/access และ memory ของตัวเอง จุดสำคัญของ Bot Mode คือทำให้ Profile เหล่านี้คุยและส่งต่องานกันได้ง่ายขึ้น

3 วิธีคุยกัน

One-on-one คุณคุยกับ Bot เดียว
Direct Bot หนึ่งส่งข้อความให้อีก Bot
Group chat หลาย Bot ทำงานในห้องเดียวกัน โดยมีเพดานการโต้ตอบเพื่อไม่ให้วนลูป

ประโยคที่ควรจำ

“It was never the bots, it's the coordination.” แนวคิดของระบบคือย้ายภาระการประสานงานออกจากคน ให้ Orchestrator และ Bot เฉพาะทางรับช่วงกันเอง

ทดลองก่อนสร้าง
Prompt — เลือกว่าจะใช้ Bot เดียวหรือทีม 
ฉันมี workflow นี้: [อธิบายงานที่ทำซ้ำ]

ช่วยวิเคราะห์ก่อนว่า งานนี้ควรใช้ Hermes Bot ตัวเดียว หรือควรแยกเป็นทีมหลาย Bot

ให้ตอบเป็น:
1) งานหลักที่ต้องทำ
2) จุดที่ต้องใช้ความเชี่ยวชาญต่างกัน
3) จุดที่ต้องส่งต่องาน
4) ถ้าใช้ Bot เดียว จะติดตรงไหน
5) ถ้าใช้หลาย Bot ควรเริ่มขั้นต่ำกี่ตัว และแต่ละตัวมี “หนึ่งงานหลัก” อะไร

อย่าเพิ่งสร้าง Bot จนกว่าจะอธิบายเหตุผลให้ชัด

03
Identity & Rules

Soul ที่ดี = ขอบเขตงานที่พูดชัด

คำอธิบาย Bot กลายเป็นพื้นฐานของ Soul — บุคลิกและกติกา ผู้พูดยกตัวอย่าง Sales Agent ที่ “ห้ามคุยเรื่องราคาโดยไม่ได้รับอนุมัติ” และ “ต้องส่งผลกลับไปที่ Hermes หลัก”

โครงสร้าง Soul ที่ใช้ทดลองได้

MissionReporting lineResponsibilitiesBoundariesReturn format

ยิ่งเฉพาะ ยิ่งคุมง่าย

ต้นฉบับเน้นว่า job ที่ “tight” ช่วยให้ Bot ปฏิบัติตามบทบาทได้ดีขึ้น อย่าเขียน Soul กว้างแบบ “ช่วยทุกอย่างที่จำเป็น”

Prompt — สร้าง Soul.md 
เขียน Soul สำหรับ Hermes Bot ชื่อ [ชื่อ] บทบาท [บทบาท]

บริบทงาน: [บริบท]

ใช้โครงสร้างนี้:
# Mission
เป้าหมายหลัก 1 ข้อ

# Reporting Line
รับงานจากใคร และต้องส่งผลกลับไปหาใคร

# Responsibilities
หน้าที่ที่ต้องทำ 3–5 ข้อ

# Boundaries
สิ่งที่ไม่ใช่หน้าที่

# Approval Rules
สิ่งที่ต้องหยุดถามฉันก่อนเสมอ

# Handoff
เมื่อทำงานเสร็จ ให้ส่งอะไร ให้ Bot ไหน / Orchestrator แบบใด

# Quality Bar
เกณฑ์ขั้นต่ำก่อนบอกว่างานเสร็จ

เขียนให้สั้น เฉพาะ และตรวจสอบได้ หลีกเลี่ยงคำสั่งกว้าง ๆ
สำคัญ: กฎใน Soul เป็นชั้น “อ่อน” เมื่อเทียบกับการไม่ให้ Tool หรือใช้ approval gate จริง ๆ ดังนั้นอย่าใช้ Soul เป็นล็อกความปลอดภัยเพียงชั้นเดียว

04
Prune

ให้ Bot เฉพาะ “กุญแจ” ที่งานนั้นต้องใช้

นี่คือขั้นที่ต้นฉบับบอกว่าคนมักข้าม: Skills เป็น workflow ที่โหลดเมื่อจำเป็น ส่วน Tools และ MCP สามารถเพิ่ม context ในแต่ละข้อความ จึงควรปิดทุกอย่างที่ Bot ไม่ต้องใช้

ประเภทความหมายตามต้นฉบับแนวทาง
SkillsSaved workflows; โหลดเมื่อจำเป็นไม่ใช่จุดหลักที่ต้องปิดเพื่อประหยัด context
Toolsการกระทำ live เช่นอ่านไฟล์ ค้นเว็บ ส่งข้อความเปิดเฉพาะที่งานต้องใช้
MCPsเชื่อมบริการภายนอก เช่น Gmail, Notion, GitHubตัดตัวที่ไม่เกี่ยวข้องออก โดยเฉพาะตัวที่มี schema/tool จำนวนมาก
Prompt — Audit Tools / MCP แบบ Least Privilege 
นี่คือหน้าที่ของ Bot: [วาง Soul หรือ job description]
นี่คือ Tools/MCP ที่เปิดอยู่: [รายการ]

ช่วย audit แบบ least privilege:
1) MUST HAVE — ถ้าไม่มีจะทำงานหลักไม่ได้
2) NICE TO HAVE — มีประโยชน์แต่ไม่จำเป็น
3) TURN OFF — ไม่เกี่ยวกับงานหลัก
4) HIGH RISK — สามารถส่งข้อความ, ลบข้อมูล, ใช้เงิน, แก้ข้อมูลสำคัญ หรือกระทบลูกค้า

สำหรับทุกตัวที่เสนอให้เปิด ให้บอกเหตุผล 1 บรรทัด
เป้าหมายคือให้ Bot มี capability น้อยที่สุดที่ยังทำงานได้ครบ

ตัวอย่างในต้นฉบับ

Sales Agent เชื่อม CRM เพราะต้องค้น/แก้/จัดเรียง leads — Bot อื่นไม่จำเป็นต้องมีสิทธิ์นั้น

ผลที่ผู้พูดคาดหวัง

Bot เร็วขึ้น ถูกลง และมีโอกาสทำสิ่งนอกขอบเขตน้อยลง เพราะ context และ capability ไม่บวมโดยไม่จำเป็น

05
Model Strategy

ใช้ Model แพงตรงที่ “ต้องคิด”

ต้นฉบับแนะนำให้ Orchestrator ซึ่งตัดสินใจและแก้ปัญหาซับซ้อนใช้โมเดลที่แข็งแรง ส่วน worker ที่ทำงานง่ายกว่าใช้โมเดลราคาถูกกว่า หรือ local model เพื่อคุมค่าใช้จ่าย

Orchestrator

วางแผน • ตัดสินใจ • แบ่งงาน • ตรวจการส่งต่อ • สรุปผลกลับหาคุณ → ใช้ model ที่เชื่อถือได้สำหรับ reasoning

Worker Bots

งานซ้ำ/เฉพาะทาง/ขั้นตอนชัด → ทดลองลดระดับ model แล้ววัดว่าคุณภาพยังผ่านเกณฑ์หรือไม่

Prompt — ทำ Model Budget Map 
ฉันมีทีม Bot ดังนี้:
[ชื่อ Bot + หน้าที่ + ความเสี่ยงของความผิดพลาด]

ช่วยแบ่งแต่ละ Bot เป็น 3 ระดับ:
A) ต้องใช้ reasoning สูง / ตัดสินใจสำคัญ
B) งานเฉพาะทางปานกลาง
C) งาน routine ที่มีรูปแบบชัด

เสนอ “ระดับความสามารถของ model” ที่เหมาะกับแต่ละตัว โดยไม่ยึดติดชื่อรุ่น
พร้อมบอก:
- เหตุผล
- วิธีทดสอบก่อนลด model
- เกณฑ์ว่าคุณภาพตกจนต้องกลับไปใช้ model ที่แข็งแรงขึ้นเมื่อไร

หลักการ: จ่ายความฉลาดตรงที่มันเปลี่ยนผลลัพธ์จริง
อย่าตีความเป็นสูตรตายตัว: ต้นฉบับให้หลัก “strong orchestrator / cheaper workers” แต่ไม่ได้ระบุ benchmark ว่า model รุ่นใดเหมาะกับงานใด คุณควรทดสอบกับงานจริงและเกณฑ์คุณภาพของตัวเอง

06
Runtime

จำเท่าที่จำเป็น และให้เวลางานยาวพอจะจบ

แนวทางในต้นฉบับ: ถ้ามี shared memory provider ให้ Orchestrator เป็นตัวหลักที่เขียน shared memory ส่วน worker ใช้ built-in memory เพื่อลดการบันทึกซ้ำ; สามารถเพิ่มจำนวน warm bots และขยาย timeout สำหรับ workflow ยาว

Memory Policy

Orchestrator → shared memory (ถ้าใช้)
Workers → built-in memory
เหตุผลตามต้นฉบับ: ลดการ double-save และ context ที่ไม่จำเป็น

Warm + Timeout

ผู้พูดยกตัวอย่างเพิ่ม warm bots จาก 3 เป็น 5 และปรับ timeout จาก default 10 นาทีเป็น 20–30 นาที “ตามขนาด workflow” เพื่อไม่ให้ long job หลุดกลางทาง

Prompt — ออกแบบ Memory Policy 
ช่วยออกแบบ memory policy สำหรับทีมนี้:
[รายชื่อ Bot + หน้าที่]

แยกข้อมูลเป็น:
1) ข้อมูลที่ Orchestrator ควรจำข้ามงาน
2) ข้อมูลที่ worker ควรเก็บเฉพาะในตัวเอง
3) ข้อมูลที่ไม่ควรบันทึกเป็น memory
4) ข้อมูลที่ควรสรุปหลังงานจบก่อนบันทึก

เป้าหมาย:
- ไม่บันทึกซ้ำทุก Bot
- Orchestrator มีบริบทที่จำเป็นต่อการตัดสินใจ
- worker มี context แค่พอทำงาน
- ถ้าไม่แน่ใจ ให้ถามฉันก่อนเสนอให้จำ
ตัวเลข 3→5 และ 20–30 นาทีเป็นตัวอย่างจากผู้พูด ไม่ใช่ค่าที่เหมาะกับทุกระบบ ให้เริ่มจาก workflow จริงและเวลาที่ใช้จริง

Safety

ถามว่า “ถ้ามันทำเอง ฉันจะเสียใจเรื่องอะไร?”

ผู้พูดใช้ 3 ตัวอย่างส่วนตัว: ใช้เงิน, ส่งอะไรให้ลูกค้า, ลบของ — สิ่งเหล่านี้ต้องมี “yes” จากคนก่อน แล้ววาง gate ซ้อนหลายชั้น

ชั้นวิธีความแข็ง
1ไม่ให้ Tool — ถ้า Bot ไม่มีเครื่องมือส่งอีเมล มันก็ส่งไม่ได้แข็งที่สุดในตัวอย่าง
2Hermes Approval — safe auto-run / เสี่ยงหยุดถาม พร้อม allow once/session/always/denyHard gate ตาม setting
3Soul rule — เขียน “Never send…” ใน persona/rulesSoft layer ใช้เสริม
Prompt — สร้าง Regret List + Gate Map 
ฉันกำลังจะให้ AI Agent ทำ workflow นี้: [workflow]

ช่วยฉันสร้าง “Regret List” โดยถามว่า:
ถ้า Agent ทำสิ่งนี้เองโดยไม่ถาม แล้วผิดพลาด ฉันจะเสียใจจริงหรือไม่?

จัดทุก action เป็น:
GREEN — ทำเองได้
YELLOW — ทำได้ แต่ต้องมีเงื่อนไข/ตรวจสอบ
RED — ต้องขออนุมัติก่อนทุกครั้ง

สำหรับ RED ทุกข้อ เสนอ gate 3 ชั้น:
1) Tool restriction: ปิด/ไม่ให้ capability อะไร
2) Approval gate: จุดไหนต้องหยุดถาม
3) Soul reinforcement: ประโยคกฎสั้น ๆ ที่ใช้ย้ำ

ห้ามใช้ Soul เป็นมาตรการเดียวสำหรับ action ที่มีผลย้อนกลับยาก

ตัวอย่าง Red Actions

ใช้เงิน • ส่งให้ลูกค้า • ลบไฟล์/ข้อมูล

หลักการ

อิสระในงานปลอดภัย แต่สิ่งที่ “เสียใจทีหลัง” ต้องอยู่หลัง approval gate

Build the Team

ประกอบ Orchestrator + Specialists ให้ส่งต่องานกัน

ตัวอย่างจริงในต้นฉบับคือ Content Team: Hermes หลักเป็น Orchestrator/Operator, Researcher หาแนวคิด และ Creator เปลี่ยนงานวิจัยเป็น content โดยผู้ใช้ต้องการคุยกับ Orchestrator เป็นจุดเดียว

คุณ→Orchestrator→Researcher→Creator→Research Check→Orchestrator→คุณ
Prompt — ให้ Orchestrator สร้างทีม 
Hermes ช่วยฉันสร้างทีมสำหรับ workflow นี้: [workflow]

เป้าหมาย:
- ฉันต้องการคุยกับคุณ (Orchestrator) เป็นจุดติดต่อหลักเพียงตัวเดียว
- คุณเป็นคนประสานงาน แบ่งงาน ตรวจ handoff และสรุปผลกลับมา
- specialist แต่ละตัวต้องมีงานหลักแคบ ๆ

เริ่มด้วยการถามฉันจนกว่าจะชัดเจนเรื่อง:
1) เป้าหมาย
2) input / output
3) style / brand / constraints
