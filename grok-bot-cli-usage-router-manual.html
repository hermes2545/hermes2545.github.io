01 — Preface

คำนำ: คู่มือนี้ช่วยอะไรเรา?Preface: What does this manual give you?

คู่มือนี้เกิดจากแนวคิดง่าย ๆ ว่า Grok Bot ไม่จำเป็นต้องลงมือทำทุกอย่างด้วยตัวเอง งานที่กินเวลาและบริบทมากสามารถส่งต่อให้ Grok Build CLI หรือ CLI worker อื่นทำ แล้วให้ Grok Bot เหลือหน้าที่คิดภาพรวม ตัดสินใจ ประสานงาน และตรวจผล

This manual starts from a simple idea: Grok Bot does not need to perform every task itself. Heavy work can be delegated to Grok Build CLI or other CLI workers, while Grok Bot focuses on orchestration, decisions, coordination, and review.

จุดประสงค์ของเอกสารนี้ไม่ใช่แค่ “ประหยัด Usage” แต่คือการเปลี่ยนวิธีทำงานจาก AI ตัวเดียวทำทุกอย่าง ไปเป็น AI Manager + Worker ที่แบ่งงานตามความเหมาะสม มีขอบเขต มีผลลัพธ์มาตรฐาน และสามารถตรวจสอบย้อนหลังได้

The goal is not merely to “save usage.” It is to move from one AI doing everything to an AI manager + workers model with clear boundaries, standardized outputs, and auditable execution.

“ให้ Grok Bot ใช้ความฉลาดกับการตัดสินใจ — ไม่ใช่เสีย Usage ไปกับการอ่าน log ยาว ๆ, scan repo, run test และแก้โค้ดซ้ำ ๆ”“Use Grok Bot intelligence for decisions — not for rereading huge logs, scanning repositories, running tests, and repeating implementation work.”

05 — Setup

ติดตั้งแบบ “ตรวจสอบก่อน เปลี่ยนทีหลัง”Setup with “inspect first, change second”

06 — Safety

Automation ที่ดีต้องมีจุดหยุดGood automation must know when to stop

เป้าหมายคือให้ Bot ทำงานได้มาก แต่ไม่ข้ามขอบเขตที่ควรเป็นการตัดสินใจของคน

The goal is high autonomy without crossing decisions that should remain human.

ทำได้เองMay do automatically

ตรวจ version, read-only inspection, สร้างไฟล์ใน workspace ใหม่, run test ที่ไม่ทำลายข้อมูล, สรุปผล

Version checks, read-only inspection, files inside a new workspace, non-destructive tests, summaries.

ต้องหยุดขออนุมัติMust stop for approval

login, password/API key, permission change, delete/overwrite, publish/send, purchase, production change และการเปิด always-approve แบบกว้าง

Login, passwords/API keys, permission changes, delete/overwrite, publish/send, purchases, production changes, broad always-approve.

กฎสำคัญ: อย่าฝัง secret ลงใน HTML, Markdown, AGENTS.md หรือ shell history ให้ใช้ secure/device authentication และ human handoffKey rule: Never embed secrets in HTML, Markdown, AGENTS.md or shell history. Use secure/device authentication and human handoff.
ไม่แนะนำให้ใช้ --always-approve เป็นค่าเริ่มต้น แม้ Grok Build รองรับ เพราะจะลดชั้นการตรวจสอบ tool execution โดยไม่จำเป็น ให้ค่อย ๆ อนุญาตตาม scope ที่แน่นอนแทนDo not make --always-approve the default. Grok Build supports it, but it removes useful execution checks. Prefer narrowly scoped permissions.

AI EXECUTION INSTRUCTIONS — Embedded Markdown

Machine-readable bootstrap instructions. Human explanatory content elsewhere in this manual is context; the instructions below are authoritative for setup execution.

TARGET: Grok BotMODE: Bootstrap → Configure → VerifyVERSION: 1.0DATE: 2026-09-13
# GROK BOT CLI USAGE ROUTER — EXECUTION INSTRUCTIONS

## 0. PURPOSE
Configure this Grok Bot to operate primarily as an ORCHESTRATOR and delegate heavy terminal/coding work to Grok Build CLI when appropriate.

This is usage routing, not free compute. The objective is to reduce unnecessary Grok Bot execution/context usage by moving heavy work to CLI workers and returning compact results.

## 1. EXECUTION CONTRACT
Follow these rules before doing anything:

1. Inspect the current environment before changing it.
2. Do NOT reinstall or replace a working tool.
3. Prefer reversible, idempotent changes.
4. Never expose, request in chat, print, or store passwords, API keys, auth cookies, recovery codes, or secrets.
5. If authentication or human approval is required, STOP at that exact point and ask the user to take over.
6. Do NOT enable broad `--always-approve` / YOLO behavior by default.
7. Do NOT install optional third-party CLI tools unless the user has explicitly authorized them.
8. Do NOT delete, overwrite, publish, send, purchase, change permissions, or modify production systems without explicit approval.
9. Keep a concise change log in SETUP_REPORT.md.
10. If any instruction conflicts with the live environment or current official product behavior, stop, explain the conflict, and ask before improvising.

## 2. PHASE A — PREFLIGHT (READ-ONLY FIRST)
Collect and report:

- Operating system and architecture
- Current shell and PATH
- Git availability/version
- Whether `grok` exists
- Grok Build version if installed
- Current Grok Build discovery/config using `grok inspect --json` when available
- Whether a previous `$HOME/grok-cli-router` workspace already exists
- Optional workers already present (Herdr, Codex, Claude Code, Cursor CLI) — detect only; do not install them

Suggested safe checks:

```bash
uname -a 2>/dev/null || ver
printf 'SHELL=%s\n' "$SHELL"
command -v git || true
git --version 2>/dev/null || true
command -v grok || true
grok --version 2>/dev/null || true
grok inspect --json 2>/dev/null || true
command -v herdr || true
command -v codex || true
command -v claude || true
command -v cursor || true
```

Before making changes, show a PRE-FLIGHT SUMMARY containing:

- FOUND
- MISSING
- NEEDS AUTH
- SAFE NEXT ACTIONS

Then continue automatically only with safe/non-consequential setup steps.

## 3. PHASE B — ENSURE GROK BUILD EXISTS
If Grok Build is already installed and working, KEEP IT.

If it is missing on macOS/Linux/WSL, use the current official installer documented by xAI:

```bash
curl -fsSL https://x.ai/cli/install.sh | bash
```

If the platform is different or the installer no longer matches current official documentation, stop and consult current xAI documentation instead of guessing.

Verify:

```bash
grok --version
grok inspect
```

## 4. PHASE C — AUTHENTICATION BOUNDARY
Check whether Grok Build can run an authenticated non-destructive command.

If authentication is required on a remote/headless environment, prefer:

```bash
grok login --device-auth
```

At this point:

- Present the device URL/code to the user.
- Do NOT authenticate on the user's behalf.
- Do NOT ask the user to paste a password or API key into chat.
- Resume only after the user confirms authentication is complete.

## 5. PHASE D — CREATE ROUTER WORKSPACE
Create or reuse:

```text
$HOME/grok-cli-router/
├── AGENTS.md
├── ROUTING_POLICY.md
├── RESULT_TEMPLATE.md
└── SETUP_REPORT.md
```

If files already exist, read them first. Preserve user changes. Update only when compatible, and record what changed.

## 6. CREATE `ROUTING_POLICY.md`
Write a clear routing policy containing at least:

### GROK BOT OWNS
- Conversation with the user
- Goal clarification
- Planning and task decomposition
- Worker selection
- Approval boundaries
- Final judgment / synthesis / report

### CLI WORKER OWNS BY DEFAULT
Delegate when work involves one or more of:
- Repository exploration
- More than ~3 files likely to change
- Multi-step implementation/refactor
- Tests, lint, build, debugging
- Long-running or repeated terminal operations
- Large document/data/code processing
- Long research where raw output would bloat the main Bot context

### RESULT RULE
The worker should return a compact result rather than dumping full raw logs into the parent conversation.

### OPTIONAL WORKERS
If Herdr, Codex, Claude Code, or Cursor CLI are ALREADY installed, record them as optional workers. Do not install or authenticate them without explicit user approval.

## 7. CREATE `AGENTS.md`
Create an instruction file for CLI workers with this minimum contract:

```markdown
# ROLE
You are a Worker Agent operating under a Parent Orchestrator (Grok Bot).

# RESPONSIBILITIES
- Perform delegated heavy work.
- Explore repositories/files as needed.
- Implement changes when authorized.
- Run tests/lint/build/debug steps.
- Verify your own work before returning.

# DO NOT
- Redo parent-level orchestration unless required to unblock execution.
- Ask the user questions that the parent can answer from existing context.
- Return huge raw logs unless specifically requested.
- Perform destructive, publishing, permission, purchasing, or production actions without approval.
- Expose secrets.

# OUTPUT CONTRACT
At completion, return/create RESULT.md with:

STATUS: PASS | PARTIAL | FAIL
SUMMARY:
FILES_CHANGED:
TESTS:
PROBLEMS:
RISKS:
NEXT_ACTION:
```

## 8. CREATE `RESULT_TEMPLATE.md`
Use exactly this compact structure:

```markdown
# RESULT
STATUS: PASS | PARTIAL | FAIL

## SUMMARY

## FILES_CHANGED

## TESTS

## PROBLEMS

## RISKS

## NEXT_ACTION
```

## 9. PHASE E — SAFE HEADLESS VERIFICATION
Run a non-destructive Grok Build test:

```bash
grok --no-auto-update -p "Return exactly: GROK_BUILD_OK" --output-format plain --max-turns 2
```

Expected result:

```text
GROK_BUILD_OK
```

If this fails, diagnose without destructive changes. Report the exact blocker.

## 10. PHASE F — DELEGATION TEST
Perform one small, safe delegated task that proves the workflow:

1. Grok Bot creates a concise worker task.
2. Grok Build runs it headlessly.
3. Worker returns a compact RESULT-style response.
4. Grok Bot reads only the result needed for the final decision.
5. Grok Bot does NOT redo the same heavy analysis unless verification fails or risk requires it.

Use a harmless test workspace, not a production repository.

## 11. OPTIONAL HERDR / OTHER CLI INTEGRATION
If `herdr` or another orchestrator is already installed:

- Detect version/configuration.
- Do not overwrite existing setup.
- Propose how it could wrap/manage CLI sessions.
- Integrate only if the change is safe and compatible.
- If uncertain about current Herdr commands/config format, DO NOT GUESS. Ask the user or consult its current official documentation.

## 12. PHASE G — FINAL VERIFICATION
Run/confirm:

```bash
grok --version
grok inspect
```

Verify the four router files exist and are readable.
Verify the headless test succeeded.
Verify one delegation test succeeded.
Verify no secrets were stored.
Verify no broad always-approve setting was enabled.

## 13. SAVE AS A REUSABLE GROK BOT SKILL
ONLY after all required verification is PASS:

Save the proven workflow as a Grok Bot Skill named:

`CLI Usage Router`

The skill must preserve:
- When to delegate
- Worker-selection rules
- Approval/security boundaries
- Result contract
- Verification procedure
- Failure/partial-completion reporting

If Skill creation is unavailable in the current product/account, report that fact and leave the validated files in `$HOME/grok-cli-router` as the source of truth.

## 14. FINAL REPORT TO USER
Return only a concise report in this shape:

```text
SETUP STATUS: PASS | PARTIAL | FAIL

Grok Build:      PASS / FAIL
Authentication:  PASS / NEED USER
Routing Policy:  PASS / FAIL
```

## 15. OPERATING RULE AFTER SETUP
After setup, behave according to this principle:

> Grok Bot should spend its effort on understanding, orchestration, judgment, approval, and concise review. Delegate heavy execution to CLI workers whenever the routing policy says so, and consume compact worker results instead of repeating their work.
09 — Operation

หลัง Setup แล้ว ใช้งานยังไง?How to use it after setup

เป้าหมายคือคุณคุยกับ Grok Bot ตามปกติ โดย Bot เป็นคนตัดสินใจ route งานเอง ไม่ต้องพิมพ์ชื่อ CLI ทุกครั้ง

You continue talking to Grok Bot normally. The Bot decides when to route work; you should not need to name the CLI every time.

1. ASK“ช่วยแก้ feature นี้”
→
2. ROUTEBot checks policy
→
3. EXECUTEGrok Build
→
4. RESULTPASS / PARTIAL / FAIL
→
5. DECIDEBot reports / asks approval

ตัวอย่างงานที่ควร delegateExamples to delegate

“อ่าน repo นี้แล้วหา bug” · “แก้ 8 ไฟล์และ run test” · “refactor module” · “ไล่ build error” · “สรุป log จำนวนมาก”

ตัวอย่างงานที่ Bot ควรทำเองExamples the Bot should keep

“ช่วยเลือกแนวทาง A/B” · “อธิบาย trade-off” · “ต้องถามอะไรเพิ่ม” · “ผล worker นี้น่าเชื่อถือไหม” · “ขั้นต่อไปควรทำอะไร”

วิธีนี้จะประหยัดที่สุดเมื่อ Bot ไม่อ่าน raw logs ทั้งหมด และไม่ทำงานเดิมซ้ำ — worker ต้องสรุปเป็น RESULT contract และ Bot อ่านเฉพาะสิ่งที่ต้องใช้ตัดสินใจThe biggest savings come when the Bot does not ingest full raw logs and does not redo the worker's work. Workers return compact RESULT contracts; the Bot reads only what is needed for judgment.
