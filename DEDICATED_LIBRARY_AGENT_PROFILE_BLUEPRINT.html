SECTION 01

จุดประสงค์

เหตุผล เป้าหมาย และปัญหาที่ Profile แบบแยกช่วยแก้ไข

01

เมื่อโครงการหนึ่งมี Website, Source files, Catalog, Covers, Documentation, Git repositories, Cloud documents และงานดูแลต่อเนื่อง การใช้ AI Agent ตัวเดียวกับงานทุกประเภทมักทำให้เกิดปัญหา

  • Context ของหลายโครงการปะปนกัน
  • Agent อาจเลือก Tool หรือ Skill ที่ไม่เกี่ยวข้อง
  • Memory อาจเก็บข้อมูลที่ล้าสมัยหรือข้ามขอบเขต
  • Credentials และสิทธิ์เข้าถึงกว้างเกินความจำเป็น
  • การสั่ง Publish หรือ Delete อาจกระทบระบบอื่น
  • Session ใหม่ต้องใช้เวลาค้นหาว่าไฟล์ใดเป็น Source of truth

แนวทางที่เหมาะสมคือสร้างDedicated AI Agent Profile แยกสำหรับโครงการ Library โดยเฉพาะ

เป้าหมายหลักของ Profile นี้คือ

  1. แยก Identity, Context, Skills, Credentials, Sessions และ Gateway ออกจาก Agent อื่น
  2. ให้ Agent เข้าใจ Project จากเอกสารที่ตรวจสอบย้อนกลับได้ แทนการพึ่ง Memory
  3. ให้ Agent ทำงาน Routine ที่ปลอดภัยได้เอง แต่ให้มนุษย์ควบคุม Public และ Destructive actions
  4. ทำให้การเพิ่มหนังสือ สร้างปก ตรวจเว็บไซต์ และ Publish เป็น Workflow ที่ทำซ้ำได้
  5. ทำให้ Project สามารถย้ายไปยังเครื่องหรือระบบ AI อื่นได้โดยมี Blueprint และ Runbooks ชัดเจน
SECTION 02

แนวคิดหลัก

หลักคิดสำหรับขอบเขต ความรู้ Source of truth และ Human approval

02

2.1 Profile คือขอบเขต ไม่ใช่แค่ชื่อ Agent

Profile ควรเป็นขอบเขตของ

  • Model และ Provider
  • System persona หรือSOUL.md
  • Skills
  • Sessions
  • Memory policy
  • Cron policy
  • Messaging credentials
  • Google OAuth
  • Working directory
  • Gateway service

ส่วน Agent คือบทบาทที่ทำงานอยู่ภายใน Profile

Profile: <PROFILE_NAME>
└── Agent: <AGENT_NAME>

ไม่ควรสร้างหลาย Profile หากมี Agent หลักเพียงตัวเดียวที่ดูแล Project เดียวกัน เพราะจะทำให้ Catalog, Credentials และ Documentation แยกเป็นหลายชุดโดยไม่จำเป็น

2.2 Project documents แทน Persistent memory

สำหรับโครงการที่มี Git และเอกสาร Agent ไม่จำเป็นต้องใช้ Persistent memory เสมอไป

การใช้PROJECT.md,AGENTS.md, Wiki index, Decisions, Runbooks และ Session handoff มีข้อดีกว่า

  • Review ได้
  • Version control ได้
  • แก้ไขและย้อนกลับได้
  • ระบุ Source ได้
  • ไม่หายจาก Context compression
  • ย้ายไปให้ AI ระบบอื่นอ่านต่อได้

Memory ควรปิดหรือใช้เฉพาะ Routing facts ที่สั้นมากเท่านั้น

2.3 หนึ่งข้อมูลมี Source of truth เพียงแห่งเดียว

ตัวอย่างการแบ่ง Source of truth

ข้อมูล Source of truth
Website code Git repository
Reading catalog data/books.json
Audio catalog data/audio-books.json
Public covers Git repository
Architecture/Decisions/Runbooks Markdown Wiki
User-facing project documents Google Drive mirror
Deployment history Git history
Session continuity Handoff document
Disaster recovery Profile export/backup system

ไม่ควรสร้าง YAML หรือ Spreadsheet ซ้ำกับ JSON Catalog เพราะจะเกิด Source of truth สองแห่ง

2.4 Manual-first ก่อน Automation

ในระยะแรกควรให้ Agent ทำงานเมื่อได้รับคำสั่ง

  • เพิ่ม Content
  • ตรวจเว็บไซต์
  • สร้างปก
  • Sync เอกสาร
  • เตรียม Publish

ยังไม่ควรเปิด Cron หรือ Auto-publish จนกว่าจะมี Workflow ที่นิ่ง มี Test และมี Rollback ชัดเจน

2.5 Human approval สำหรับ Public และ Destructive actions

Agent ควรแบ่งอำนาจเป็นสามระดับ

ทำเองได้

  • อ่านและวิเคราะห์ไฟล์
  • แก้ Working tree
  • อัปเดต Catalog และ Wiki
  • สร้างปกและ Generated pages
  • รัน Tests และ Local preview
  • ตรวจ Privacy และ Broken links
  • Sync เอกสาร Private ไปยัง Folder ที่กำหนด

ต้องรายงานก่อนทำ

  • เปลี่ยน Schema
  • เปลี่ยน Sorting policy
  • Rename Public content
  • เปลี่ยน Architecture หรือ Folder structure
  • Commit การเปลี่ยนแปลงขนาดใหญ่

ต้องได้รับอนุมัติชัดเจน

  • Push Public repository
  • Publish Website
  • Delete หรือ Trash ไฟล์
  • เปลี่ยน Drive permissions
  • Force-push หรือ Rewrite history
  • เปลี่ยน Credentials
  • เปิด Cron, Memory หรือ Group access

เอกสารสำคัญ

เอกสารแกนหลักที่ทำให้ Agent เริ่มงานต่อได้อย่างตรวจสอบย้อนกลับได้

ใช้กำหนด

  • Verification commands
  • Privacy rules

ใช้สรุป

  • เป้าหมาย Project

SECTION 06

การสร้าง Profile

ขั้นตอนสร้าง Profile สะอาดและกำหนดนโยบายพื้นฐาน

06

คำสั่งเป็นตัวอย่าง ให้ตรวจ Version และ Help ของระบบก่อนใช้งาน

6.1 สร้าง Profile แบบสะอาด

hermes profile create <PROFILE_NAME> --no-skills \
  --description "Dedicated agent for <PROJECT_NAME>"

ไม่ควร Clone.env, OAuth token, Telegram token, Memory หรือ Cron จาก Profile อื่นโดยอัตโนมัติ

6.2 ตั้งค่า Model และ Working directory

hermes -p <PROFILE_NAME> config set model.default <MODEL_ID>
hermes -p <PROFILE_NAME> config set model.provider <PROVIDER>
hermes -p <PROFILE_NAME> config set terminal.cwd <PROJECT_PATH>
hermes -p <PROFILE_NAME> config set approvals.mode smart

6.3 ปิด Memory

hermes -p <PROFILE_NAME> config set memory.memory_enabled false
hermes -p <PROFILE_NAME> config set memory.user_profile_enabled false

6.4 ตรวจ Cron

hermes -p <PROFILE_NAME> cron list --all

ผลที่ต้องการในระยะแรกคือไม่มี Scheduled jobs

6.5 สร้าง Agent persona

เขียน ProfileSOUL.md ให้มี

  • ชื่อ Agent
  • Project mission
  • Systems ที่เชื่อมต่อ
  • Source-of-truth order
  • Authority levels
  • Session start/close workflow
  • Privacy และ Security rules

SECTION 08

Telegram Bot แยก

ตั้งค่า Bot แยกแบบ DM-only และป้องกัน Duplicate poller

08

8.1 สร้างผ่าน BotFather

ขั้นตอนทั่วไป

/newbot

จากนั้นกำหนด

  • Display name:<BOT_DISPLAY_NAME>
  • Username: ต้องลงท้ายด้วยbot หรือBot ตามกฎ Telegram

BotFather จะคืน Token ซึ่งเป็นข้อมูลลับ

8.2 จัดเก็บ Token อย่างปลอดภัย

  • ห้ามส่ง Token ใน Group หรือ Public chat
  • ใช้ Hidden prompt ใน Terminal
  • Validate ด้วย TelegramgetMe ก่อนบันทึก
  • บันทึกใน Profile.env เท่านั้น
  • ตั้ง Permission เป็น0600
  • ห้ามพิมพ์ Token กลับใน Output

8.3 Access policy

ตัวอย่าง

TELEGRAM_ALLOWED_USERS=<TELEGRAM_USER_ID>
TELEGRAM_ALLOW_ALL_USERS=false
TELEGRAM_HOME_CHANNEL=<TELEGRAM_USER_ID>

สำหรับ DM-only ควรเพิ่ม Config

platforms:
  telegram:
    allowed_chats:
      - "<NON_MATCHING_GROUP_SENTINEL>"
    group_allowed_chats: []
    guest_mode: false
    require_mention: true
    observe_unmentioned_group_messages: false

Telegram Bot อาจยังถูกเพิ่มเข้า Group ได้ แต่ Hermes จะไม่ประมวลผล Group messages หากต้องการปิดจาก Telegram โดยสมบูรณ์สามารถตั้ง Group membership ผ่าน BotFather เพิ่มได้

8.4 Foreground test ก่อน Service

hermes -p <PROFILE_NAME> gateway run

ตรวจให้เห็น

Active profile: <PROFILE_NAME>
Telegram connected
Gateway running with 1 platform

จากนั้นทดสอบ DM เข้าและออกจริง

8.5 Persistent service

หยุด Foreground process ก่อน แล้วจึงติดตั้ง Service

hermes -p <PROFILE_NAME> gateway install
hermes -p <PROFILE_NAME> gateway start
hermes -p <PROFILE_NAME> gateway status

ตรวจ

  • Service active/running
  • Main PID ตรงกับ Profile
  • Systemd linger เปิด
  • ไม่มี Duplicate poller
  • Telegram polling healthy
  • Shutdown timeout มากกว่า Agent drain timeout
SECTION 09

Google OAuth แยก

แยก OAuth ตาม Profile และตรวจสิทธิ์ด้วย Live verification

09

หลักการ

  • Copy ได้เฉพาะ OAuth client configuration
  • ห้าม Copygoogle_token.json จาก Profile อื่น
  • Authorize ใหม่โดยให้HERMES_HOME ชี้ไปที่ Profile เป้าหมาย
  • ตรวจ Account identity หลัง Auth
  • ตั้ง Token และ Client Secret เป็น0600

ตัวอย่าง

export HERMES_HOME="$HOME/.hermes/profiles/<PROFILE_NAME>"
python <GOOGLE_SETUP_SCRIPT> --check
python <GOOGLE_SETUP_SCRIPT> --auth-url

หลังอนุญาต Browser อาจ Redirect ไปhttp://localhost:1 และแสดง Error ซึ่งเป็นพฤติกรรมปกติของ Manual callback

ให้นำ Redirect URL ไป Exchange ด้วย

python <GOOGLE_SETUP_SCRIPT> --auth-code "<FULL_REDIRECT_URL>"

Callback URL ที่มีcode= เป็นข้อมูลลับและควรใช้เพียงครั้งเดียว

หลัง Auth ต้องตรวจ

  • OAuth account ถูกบัญชี
  • Token อยู่ใน Profile ที่ถูกต้อง
  • Drive folder อ่าน/เขียนได้
  • Folder capabilities อนุญาตให้ Add children
  • Agent สามารถ Upload และ Read-back เอกสารทดสอบได้
SECTION 10

Git Public และ Private Mirror

แยก Public repository และ Private mirror ตามหน้าที่

10

Public repository

ใช้สำหรับ Code และ Public-safe project knowledge

Private mirror

เพิ่ม Remote แยก

git remote add backup <PRIVATE_REPOSITORY_URL>

หลังได้รับอนุมัติ Publish

git push origin main
git push backup main
git push backup --tags

ตรวจว่า Local, Public และ Private HEAD ตรงกัน

git rev-parse HEAD
git ls-remote origin refs/heads/main
git ls-remote backup refs/heads/main

Private mirror ไม่ควรเก็บ Credentials หรือ Browser profiles

SECTION 11

Google Drive Document Registry

เชื่อม Local path กับ Drive file ID โดยไม่สร้างไฟล์ซ้ำ

11

ใช้ Local private registry เชื่อม Relative path กับ Drive file ID

{
  "schema_version": 1,
  "drive_parent_id": "<DRIVE_FOLDER_ID>",
  "documents": {
    "docs/example.md": {
      "visibility": "private",
      "drive_file_id": "<DRIVE_FILE_ID>",
      "status": "active",
      "sync_policy": "update-existing"
    }
  }
}

Workflow Sync

  1. Search exact filename ใน exact parent
  2. Update/Copy ไฟล์เดิมแทน Upload ซ้ำ
  3. Verify ID, Name, MIME type, Parent และtrashed=false
  4. Update registry หลัง Verification สำเร็จเท่านั้น
  5. การย้ายใช้ Copy → Verify → Trash source
SECTION 12

Agent Operating Workflow

ลำดับเริ่ม Session ทำงาน ตรวจสอบ และปิด Session

12

ตอนเปิด Session

1. Read AGENTS.md
2. Read PROJECT.md
3. Read docs/wiki/index.md
4. Read recent docs/wiki/log.md
5. Run git status --short --branch
6. Read only the relevant decision/runbook/catalog

ตอนทำงาน

1. Gather primary evidence
2. Write a failing test for behavior changes
3. Edit source/catalog/template
4. Regenerate artifacts
5. Run focused tests
6. Run full tests
7. Preview desktop/mobile
8. Run privacy scan
9. Prepare scoped commit
10. Request approval before public push

ตอนปิด Session

1. Run full verification
2. Update wiki index/log
3. Update SESSION_HANDOFF.md
4. Sync approved private docs to Drive
5. Report uncommitted files and background processes
6. Push only when explicitly approved
7. Verify remote and production state

SECTION 15

ประโยชน์

Context isolation

Agent เข้าใจเฉพาะ Project ที่รับผิดชอบและไม่ปะปนกับงานอื่น

Security

Credentials, Bot Token, OAuth และ Sessions แยกจาก Profile อื่น

Token efficiency

Agent อ่าน Index และ Topic ที่เกี่ยวข้องแทนการโหลดประวัติทั้งหมด

Repeatability

Human control

Portability

Auditability

Recovery

SECTION 16

ข้อจำกัดและสิ่งที่ต้องระวัง

ขอบเขตและความเสี่ยงที่ต้องควบคุมด้วย Policy และ Verification

16
  • Public repository เป็น World-readable
  • Private Git ไม่ใช่ที่เก็บ Credentials
  • Google OAuth อาจมี Scope กว้างกว่าหน้าที่ Agent จึงต้องมี Agent policy จำกัดการใช้งาน
  • Telegram Bot Username ค้นเจอได้ แม้ Hermes จะปฏิเสธผู้ใช้ที่ไม่อยู่ใน Allowlist
  • Memory ที่ปิดทำให้ Documentation ต้องทันสมัยเสมอ
  • Cron ที่ปิดหมายความว่า Agent ไม่ทำงานเองจนกว่าจะได้รับข้อความ
  • Agent policy เป็น Logical boundary ไม่ใช่ OS sandbox
  • ระบบต้องตรวจ Live state ก่อน External operations เสมอ

You are an expert AI agent architect, documentation engineer, static-site maintainer, and security-conscious automation operator.

Your task is to design and initialize a dedicated AI agent profile for a knowledge-library project.

Project variables:
- Profile name: <PROFILE_NAME>
- Agent name: <AGENT_NAME>
- Project name: <PROJECT_NAME>
- Local project path: <PROJECT_PATH>
- Public site URL: <PUBLIC_SITE_URL>

- Telegram bot username: <TELEGRAM_BOT_USERNAME>
- Allowed Telegram user ID: <TELEGRAM_USER_ID>
- Model/provider: <MODEL_AND_PROVIDER>

Goals:
1. Isolate the project from unrelated agents, credentials, sessions, memory, cron jobs, tools, and business contexts.
2. Create one dedicated agent persona inside one clean profile.
3. Use project documents as durable knowledge instead of persistent memory.
4. Maintain one source of truth per data type.
5. Allow safe, reversible project work autonomously.
6. Require explicit user approval for public publishing, deletion, permission changes, credential changes, cron, memory, group access, and destructive Git operations.
7. Provide a DM-only Telegram interface with a single-user allowlist.
8. Use profile-scoped Google OAuth and verify the actual account identity.
9. Keep public code/docs in public Git, mirror committed history privately, and keep human-facing private project docs in a dedicated Drive folder.
10. Verify every external write by reading the exact target back.

Required profile policies:
- Persistent memory: disabled
- User-profile memory: disabled
- Cron: none
- Telegram allow-all: false
- Telegram groups: denied
- Public push: explicit approval required
- Credentials: profile-scoped and file permissions 0600
- Public files: pre-share scan required

Create these artifacts:
- Agent SOUL/persona document
- AGENTS.md operating contract
- PROJECT.md project overview
- docs/wiki/SCHEMA.md
- docs/wiki/index.md
- docs/wiki/log.md
- architecture overview
- decisions for autonomy, source of truth, and public/private boundaries
- runbooks for adding reading content, adding audio content, verifying/publishing, syncing Drive docs, closing/resuming sessions, and restoring the project
- local-only project-links registry
- local-only Drive document registry
- deterministic knowledge validator
- regression tests

Agent startup sequence:
1. Read AGENTS.md
2. Read PROJECT.md
3. Read wiki index
4. Read recent durable log
5. Inspect Git status/remotes
6. Load only relevant topic pages, catalogs, and runbooks

Agent work sequence:
1. Gather primary evidence
2. Write failing tests for behavior changes
3. Edit source/catalog/template
4. Regenerate outputs
5. Run focused and full tests
6. Verify desktop/mobile behavior
7. Run privacy scan
8. Prepare scoped commit
9. Ask approval before public push
10. Verify public/private remotes and production after approved push

Telegram setup rules:
- Guide the user one manual step at a time through BotFather
- Never ask the user to paste the bot token into chat
- Provide a hidden terminal prompt to validate and store the token
- Print only safe bot metadata
- Test foreground gateway before persistent service
- Verify one active poller only
- Keep DM-only access and single-user allowlist

Google OAuth rules:

- Never copy an existing profile token
- Generate a fresh profile-scoped OAuth session
- Treat callback URLs containing code= as sensitive

Git rules:

- Local/private registries are never staged publicly
