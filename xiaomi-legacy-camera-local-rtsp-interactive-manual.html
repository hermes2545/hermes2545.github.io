แก้ปัญหากล้อง Xiaomi รุ่นเก่าภาพดีเลย์ด้วย Local RTSP BridgeFixing High Latency on Legacy Xiaomi Cameras with a Local RTSP Bridge

เอกสารนี้เป็นแนวทางทั่วไปสำหรับผู้ใช้ Home Assistant ที่มีกล้อง Xiaomi / Mi Home / Xiaomi Home รุ่นเก่าบางรุ่น ซึ่งดูภาพผ่าน integration หรือ cloud stream แล้วเกิดอาการดีเลย์สะสมหลายวินาที หลายนาที หรือหนักกว่านั้น
ตัวอย่างทั้งหมดใช้ placeholder ทั่วไป เช่น <VISION_SERVER_IP> และ <CAMERA_DID> เพื่อให้เผยแพร่สาธารณะได้โดยไม่เปิดเผยข้อมูลระบบจริง

This document is a general guide for Home Assistant users who have certain older Xiaomi / Mi Home / Xiaomi Home cameras where viewing through an integration or cloud stream develops accumulated delay of several seconds, several minutes, or even worse.
All examples use generic placeholders such as <VISION_SERVER_IP> and <CAMERA_DID> so the guide can be published publicly without exposing real system information.

1. ปัญหาเดิมคืออะไร1. What is the original problem?

กล้อง Xiaomi รุ่นเก่าหลายรุ่น โดยเฉพาะกล้องที่อยู่ในระบบ Xiaomi Home / Mi Home และไม่มี RTSP local โดยตรง มักมีปัญหาเมื่อนำเข้า Home Assistant ผ่าน integration แบบ cloud หรือผ่าน stream endpoint ที่ Xiaomi สร้างให้

อาการที่พบบ่อยคือ:

  • ภาพใน Home Assistant ดีเลย์มากกว่าที่ควร
  • ตอนแรกดีเลย์น้อย แต่ยิ่งเปิดไว้นานยิ่งดีเลย์สะสม
  • ภาพค้างหรือกระโดดเป็นช่วง ๆ
  • entity ของกล้องขึ้น unavailable เป็นบางเวลา
  • integration เห็นตัวกล้อง แต่ไม่ได้สร้าง camera.* entity ที่ใช้งาน live stream ได้จริง
  • บาง integration ให้ได้แค่ปุ่ม start_hls_stream, start_rtsp_stream, start_p2p_stream แต่ไม่ได้ให้ URL local stream ที่เสถียร
  • ดูในแอป Xiaomi เองยังพอใช้ได้ แต่พอเข้า Home Assistant แล้วภาพช้าหรือสะสม delay

Many older Xiaomi camera models, especially cameras inside the Xiaomi Home / Mi Home ecosystem that do not provide direct local RTSP, can have problems when added to Home Assistant through a cloud-based integration or through a stream endpoint generated by Xiaomi.

Common symptoms include:

  • Video in Home Assistant is more delayed than it should be.
  • Delay is small at first, but keeps accumulating the longer the stream remains open.
  • Video freezes or jumps intermittently.
  • The camera entity sometimes becomes unavailable.
  • The integration can see the camera device, but does not create a usable camera.* entity for a real live stream.
  • Some integrations expose only buttons such as start_hls_stream, start_rtsp_stream, or start_p2p_stream, but do not provide a stable local stream URL.
  • The Xiaomi app itself remains usable, but video becomes slow or accumulates delay after being brought into Home Assistant.

2. สาเหตุที่ภาพดีเลย์2. Why does the video become delayed?

สาเหตุหลักไม่ได้เกิดจาก Home Assistant เพียงอย่างเดียว แต่เกิดจากเส้นทางวิดีโอเดิมที่อ้อมผ่าน cloud และ protocol ที่ไม่ได้ออกแบบมาสำหรับ local low-latency dashboard

เส้นทางเดิมมักเป็นประมาณนี้:

Xiaomi Camera
  → Xiaomi Cloud / P2P / HLS / cloud proxy
  → Home Assistant integration
  → Home Assistant camera entity / dashboard
  → browser / mobile app

ปัญหาของเส้นทางนี้คือ:

2.1 Cloud / P2P มี buffer ของตัวเอง

เมื่อ stream ถูกส่งผ่าน Xiaomi Cloud หรือ P2P relay ระบบมักมี buffer เพื่อกันภาพกระตุก ซึ่งดีสำหรับแอปมือถือทั่วไป แต่ไม่ดีสำหรับ Home Assistant dashboard ที่ต้องการภาพใกล้ real-time

2.2 HLS มี latency โดยธรรมชาติ

ถ้า integration ใช้ HLS stream ภาพมักดีเลย์อยู่แล้ว เพราะ HLS แบ่งวิดีโอเป็น segment เช่น 2–6 วินาทีต่อ segment แล้ว browser ต้องรอ segment ก่อนเล่น

ผลคือ latency อาจเริ่มที่หลายวินาที และถ้า stream ไม่ sync ดีพอ อาจเกิด delay สะสมได้

2.3 Stream ถูกแปลงหลายชั้น

บางระบบแปลงแบบนี้:

Camera → Xiaomi cloud stream → HLS/RTSP temp URL → HA stream proxy → dashboard card

ทุกชั้นอาจเพิ่ม buffer อีกเล็กน้อย พอรวมกันแล้วดีเลย์มาก

2.4 กล้องรุ่นเก่าไม่มี RTSP local ให้เปิดตรง ๆ

กล้อง IP หลายยี่ห้อมี RTSP local URL เช่น:

rtsp://camera-local-ip/live

แต่กล้อง Xiaomi รุ่นเก่าหลายรุ่นไม่ได้เปิด RTSP local ให้ผู้ใช้โดยตรง จึงต้องอาศัย cloud/P2P integration แทน

2.5 Integration เห็นกล้องแต่ไม่ expose live stream ที่เหมาะสม

บาง integration เห็น device และ properties ได้ เช่น on/off, night mode, motion, stream status แต่ไม่ได้ให้ camera entity ที่เหมาะสำหรับ live view หรือ local low latency

The main cause is not Home Assistant alone. The delay is usually caused by the original video path being routed through the cloud and through protocols that were not designed for a local low-latency dashboard.

The original path is often similar to this:

Xiaomi Camera
  → Xiaomi Cloud / P2P / HLS / cloud proxy
  → Home Assistant integration
  → Home Assistant camera entity / dashboard
  → browser / mobile app

Problems with this path include:

2.1 Cloud / P2P has its own buffering

When a stream is sent through Xiaomi Cloud or a P2P relay, the system usually buffers video to reduce stuttering. This is useful for a normal mobile app, but not ideal for a Home Assistant dashboard that needs video close to real time.

2.2 HLS has inherent latency

If an integration uses an HLS stream, video is normally delayed by design because HLS splits video into segments, for example 2–6 seconds per segment, and the browser has to wait for segments before playing them.

As a result, latency may begin at several seconds, and if the stream does not stay synchronized well, the delay may continue to accumulate.

2.3 The stream is converted through multiple layers

Some systems convert the stream through a path like this:

Camera → Xiaomi cloud stream → HLS/RTSP temp URL → HA stream proxy → dashboard card

Each layer can add a little more buffering. When those buffers are combined, the total delay can become large.

2.4 Older cameras may not expose direct local RTSP

Many IP cameras from other vendors provide a direct local RTSP URL such as:

rtsp://camera-local-ip/live

However, many older Xiaomi cameras do not expose local RTSP directly to the user, so cloud/P2P integration has to be used instead.

2.5 The integration sees the camera but does not expose a suitable live stream

Some integrations can see the device and its properties, such as on/off, night mode, motion, or stream status, but do not provide a camera entity suitable for live viewing or local low-latency playback.

3. แนวคิดของวิธีแก้3. Solution concept

แนวทางที่ใช้คือสร้าง “local bridge” แยกต่างหาก ให้เครื่องหนึ่งทำหน้าที่คุยกับ Xiaomi แล้ว publish stream ออกมาเป็น RTSP local ที่ Home Assistant และ go2rtc ใช้งานได้

เส้นทางใหม่เป็นแบบนี้:

Xiaomi Camera
  → Xiaomi / MiOT local bridge service
  → micam stream worker
  → local RTSP publish
  → go2rtc
  → Home Assistant dashboard

หรือเขียนง่าย ๆ:

กล้อง Xiaomi → Bridge → RTSP local → go2rtc → Home Assistant

ข้อดี:

  • ลดการพึ่ง cloud playback path ใน Home Assistant
  • ได้ RTSP URL ที่เรียกซ้ำได้ถาวร
  • ใช้ go2rtc จัดการ WebRTC / RTSP / MSE ได้ต่อ
  • ลด delay สะสมจาก HLS/cloud proxy
  • แยกงานวิดีโอหนักออกจาก Home Assistant
  • เพิ่ม/ลบ stream ได้เป็นระบบ

The approach is to create a separate “local bridge.” One machine communicates with Xiaomi and then publishes the video as a local RTSP stream that Home Assistant and go2rtc can use.

The new path looks like this:

Xiaomi Camera
  → Xiaomi / MiOT local bridge service
  → micam stream worker
  → local RTSP publish
  → go2rtc
  → Home Assistant dashboard

Or, more simply:

Xiaomi Camera → Bridge → local RTSP → go2rtc → Home Assistant

Benefits:

  • Reduces dependence on the cloud playback path inside Home Assistant.
  • Provides a reusable, persistent RTSP URL.
  • Allows go2rtc to handle WebRTC / RTSP / MSE afterward.
  • Reduces accumulated delay from HLS/cloud proxy layers.
  • Moves heavy video processing away from Home Assistant.
  • Makes adding and removing streams more systematic.

4. สถาปัตยกรรมที่แนะนำ4. Recommended architecture

ควรใช้เครื่องแยกสำหรับงานวิดีโอ เช่น mini PC, NUC, workstation, server ขนาดเล็ก หรือเครื่อง Linux ที่เปิด 24/7

เรียกเครื่องนี้แบบทั่วไปว่า:

Vision Server / Video Worker

ตัวอย่างโครงสร้าง:

[ Xiaomi Cameras ]
        │
        ▼
[ Vision Server / Video Worker ]
        ├─ Miloco / Xiaomi MiOT bridge
        ├─ micam worker per camera
        └─ go2rtc RTSP/WebRTC gateway
        │
        ▼
[ Home Assistant ]
        │
        ▼
[ Lovelace dashboard / mobile app / browser ]

แนะนำให้แยก Video Worker ออกจาก Home Assistant เพราะการดึง/แปลงวิดีโออาจใช้ CPU, network, memory และอาจทำให้ Home Assistant หน่วงได้ถ้ารันรวมกัน

Use a separate machine for video work, such as a mini PC, NUC, workstation, small server, or Linux machine that can run 24/7.

In this guide, that machine is referred to generically as:

Vision Server / Video Worker

Example architecture:

[ Xiaomi Cameras ]
        │
        ▼
[ Vision Server / Video Worker ]
        ├─ Miloco / Xiaomi MiOT bridge
        ├─ micam worker per camera
        └─ go2rtc RTSP/WebRTC gateway
        │
        ▼
[ Home Assistant ]
        │
        ▼
[ Lovelace dashboard / mobile app / browser ]

It is recommended to keep the Video Worker separate from Home Assistant because pulling and converting video may consume CPU, network bandwidth, and memory, and can make Home Assistant sluggish if everything runs on the same machine.

Component Function

micam Pull the stream from Miloco and publish it as RTSP
go2rtc Receive the RTSP publish and provide it to Home Assistant / the dashboard
Home Assistant Display the stream on dashboards and use it in automations / camera cards

6. Flow ที่แก้ delay ได้6. Flow that reduces delay

เดิม

Camera → Xiaomi Cloud/HLS/P2P → HA integration → dashboard

ปัญหา:

  • มี buffer หลายชั้น
  • delay สะสม
  • stream URL อาจเป็น temporary URL
  • HLS มี latency สูงกว่าการดูแบบ live

ใหม่

Camera → Miloco → micam → RTSP local → go2rtc → dashboard

ผลที่ต้องการ:

  • RTSP stream อยู่ใน local network
  • go2rtc จัดการ stream ให้ browser ดูแบบ low latency ได้
  • dashboard ไม่ต้องรอ cloud/HLS path เดิม
  • delay ลดลงมาก เหลือระดับ local streaming ตามสภาพ network และ codec

Before

Camera → Xiaomi Cloud/HLS/P2P → HA integration → dashboard

Problems:

  • Multiple buffering layers.
  • Accumulated delay.
  • The stream URL may be temporary.
  • HLS has higher latency than live-oriented streaming.

After

Camera → Miloco → micam → local RTSP → go2rtc → dashboard

Desired results:

  • The RTSP stream stays inside the local network.
  • go2rtc handles the stream so a browser can view it with low latency.
  • The dashboard no longer has to wait on the original cloud/HLS path.
  • Delay is greatly reduced and becomes closer to normal local-stream latency, depending on the network and codec.

7. Prerequisites7. Prerequisites

ต้องมี:

  • เครื่อง Linux สำหรับ Video Worker
  • Docker และ Docker Compose
  • Home Assistant ที่เข้าถึง Video Worker ได้ผ่าน LAN หรือ VPN ส่วนตัว
  • Xiaomi account ที่มีกล้องอยู่ใน region ถูกต้อง
  • รายชื่อกล้องและ DID ของกล้องแต่ละตัว
  • port ที่ต้องใช้ เช่น:
    • Miloco backend: <MILOCO_PORT> เช่น 18000
    • go2rtc API: 1984
    • go2rtc RTSP: 8554

ตัวอย่าง placeholder:

<VISION_SERVER_IP>      = IP ของ Video Worker
<MILOCO_PORT>           = port ของ Miloco backend
<CAMERA_DID_1>          = DID ของกล้องตัวที่ 1
<CAMERA_DID_2>          = DID ของกล้องตัวที่ 2
<STREAM_NAME_1>         = ชื่อ stream ใน go2rtc
<STREAM_NAME_2>         = ชื่อ stream ใน go2rtc

You need:

  • A Linux machine for the Video Worker.
  • Docker and Docker Compose.
  • Home Assistant that can reach the Video Worker over LAN or a private VPN.
  • A Xiaomi account containing the cameras in the correct region.
  • A list of cameras and the DID of each camera.
  • Required ports, for example:
    • Miloco backend: <MILOCO_PORT>, for example 18000
    • go2rtc API: 1984
    • go2rtc RTSP: 8554

Example placeholders:

<VISION_SERVER_IP>      = IP address of the Video Worker
<MILOCO_PORT>           = port of the Miloco backend
<CAMERA_DID_1>          = DID of camera 1
<CAMERA_DID_2>          = DID of camera 2
<STREAM_NAME_1>         = stream name in go2rtc
<STREAM_NAME_2>         = stream name in go2rtc

8. ตัวอย่าง docker-compose.yml8. Example docker-compose.yml

ตัวอย่างนี้เป็นโครงสร้างทั่วไป ต้องปรับ image/version/env ให้ตรงกับ project ที่ใช้งานจริง

services:
  miloco:
    container_name: miloco
    image: <MILOCO_IMAGE>
    network_mode: host
    environment:
      BACKEND_PORT: ${MILOCO_PORT:-18000}
      BACKEND_LOG_LEVEL: ${MILOCO_LOG_LEVEL:-warning}
      TZ: ${TZ:-Asia/Bangkok}
    volumes:
      - ./miloco:/app/miloco_server/.temp
      - ./miloco-config/server_config.yaml:/app/config/server_config.yaml:ro
      - ./miloco-config/camera_extra_info.yaml:/app/miot_kit/miot/configs/camera_extra_info.yaml:ro
    restart: unless-stopped

  go2rtc:
    container_name: go2rtc-xiaomi
    image: <GO2RTC_IMAGE>
    network_mode: host
    privileged: true
    restart: unless-stopped
    environment:
      TZ: ${TZ:-Asia/Bangkok}
    volumes:
      - ./go2rtc:/config

  micam-camera-1:
    image: <MICAM_IMAGE>
    container_name: micam-camera-1
    depends_on: [miloco, go2rtc]
    environment:
      MILOCO_BASE_URL: ${MILOCO_BASE_URL:-https://miloco:18000}
      MILOCO_PASSWORD: ${MILOCO_PASSWORD}
      CAMERA_ID: ${CAMERA_DID_1}
      RTSP_URL: ${CAMERA_1_RTSP_URL:-rtsp://miloco:8554/<STREAM_NAME_1>}
      VIDEO_CODEC: ${VIDEO_CODEC:-hevc}
      STREAM_CHANNEL: ${STREAM_CHANNEL:-0}
      TZ: ${TZ:-Asia/Bangkok}
    restart: unless-stopped
    extra_hosts:
      - "miloco:${MILOCO_HOST_IP:-host-gateway}"

  micam-camera-2:
    image: <MICAM_IMAGE>
    container_name: micam-camera-2
    depends_on: [miloco, go2rtc]
    environment:
      MILOCO_BASE_URL: ${MILOCO_BASE_URL:-https://miloco:18000}
      MILOCO_PASSWORD: ${MILOCO_PASSWORD}
      CAMERA_ID: ${CAMERA_DID_2}
      RTSP_URL: ${CAMERA_2_RTSP_URL:-rtsp://miloco:8554/<STREAM_NAME_2>}
      VIDEO_CODEC: ${VIDEO_CODEC:-hevc}
      STREAM_CHANNEL: ${STREAM_CHANNEL:-0}
      TZ: ${TZ:-Asia/Bangkok}
    restart: unless-stopped

      - "miloco:${MILOCO_HOST_IP:-host-gateway}"

17. เรื่อง PTZ17. PTZ considerations

กล้อง Xiaomi รุ่นเก่าบางรุ่นอาจไม่มี PTZ action ออกมาใน MIoT spec หรือ Home Assistant integration แม้ว่าตัวกล้องจริงจะหมุนได้ในแอป Xiaomi

สิ่งที่อาจเห็นใน Home Assistant:

  • stream start/stop buttons
  • memory card actions
  • image rollover
  • night mode
  • motion tracking status
  • camera on/off

แต่ไม่มี:

  • move left
  • move right
  • move up
  • move down

ในกรณีนี้ไม่ควรสร้างปุ่ม PTZ หลอกหรือผูกกับปุ่มของกล้องตัวอื่น เพราะจะทำให้ผู้ใช้เข้าใจผิดหรือสั่งกล้องผิดตัว

ถ้าจะทำ PTZ จริง ต้องมีอย่างใดอย่างหนึ่ง:

  1. Home Assistant expose button/action move ของกล้องนั้นโดยตรง
  2. MIoT action ที่ยืนยันแล้วว่าสั่ง pan/tilt ได้จริง
  3. API local/cloud ที่ทดสอบแล้วว่าสั่ง PTZ ได้
  4. script ที่เรียก API นั้นอย่างปลอดภัย โดยไม่เปิดเผย token/password

Some older Xiaomi cameras may not expose PTZ actions in the MIoT specification or Home Assistant integration, even if the physical camera can rotate when controlled from the Xiaomi app.

You may see the following in Home Assistant:

  • stream start/stop buttons
  • memory card actions
  • image rollover
  • night mode
  • motion tracking status
  • camera on/off

But not:

  • move left
  • move right
  • move up
  • move down

In this case, do not create fake PTZ buttons or bind the controls to buttons belonging to another camera. That could mislead the user or cause commands to be sent to the wrong camera.

To implement real PTZ, at least one of the following must exist:

  1. Home Assistant directly exposes a move button/action for that camera.
  2. A MIoT action has been verified to perform pan/tilt for that camera.
  3. A tested local/cloud API can perform PTZ.
  4. A script safely calls that API without exposing tokens or passwords.

miot:

  • Wrong region.
  • The camera model is in a denylist.
  • Wrong camera ID.
  • Wrong stream channel.
  • The bridge has not yet authorized the Xiaomi account.

streams:

18.5 FFmpeg Broken pipe

Common causes:

  • go2rtc has no stream path available for publishing.
  • micam publishes to the wrong host, for example 127.0.0.1 inside the micam container itself.
  • The RTSP URL should point to the host gateway or the network interface where go2rtc is listening.

Example for separate containers:

CAMERA_1_RTSP_URL=rtsp://miloco:8554/<STREAM_NAME_1>

extra_hosts:

docker compose up -d --force-recreate micam-camera-1

Some cameras use HEVC/H.265 and others use H.264. Check with ffprobe or the logs.

If micam supports a codec parameter and the command must be overridden, you may use:

command: micam --video-codec h264

If HEVC works, keep using HEVC because newer Xiaomi cameras / some Xiaomi models commonly output H.265.

19. ผลลัพธ์หลังแก้19. Expected result after the fix

หลังเปลี่ยนจาก cloud/HLS path มาเป็น local RTSP bridge ผลที่คาดหวังคือ:

  • เปิดภาพใน Home Assistant ได้เร็วขึ้น
  • delay ลดลงมาก
  • ไม่มี delay สะสมจาก cloud/HLS path เดิม
  • stream URL คงที่ เช่น rtsp://<VISION_SERVER_IP>:8554/<STREAM_NAME>
  • go2rtc เห็น producer ต่อเนื่อง
  • dashboard ใช้ WebRTC card ดูภาพได้ใกล้ real-time มากขึ้น

อย่างไรก็ตาม ยังมี latency เล็กน้อยตามปกติของ:

  • codec เช่น H.265
  • Wi-Fi/LAN
  • browser decoding
  • go2rtc/WebRTC pipeline
  • CPU ของ Video Worker

โดยทั่วไปแนวทางนี้ไม่ได้แปลว่า latency เป็นศูนย์ แต่แก้ปัญหา delay สะสมหลายวินาที/หลายนาทีจาก cloud path ได้อย่างชัดเจน

After switching from the cloud/HLS path to a local RTSP bridge, the expected results are:

  • Home Assistant can open the video more quickly.
  • Delay is greatly reduced.
  • There is no longer accumulated delay caused by the original cloud/HLS path.
  • The stream URL is stable, for example rtsp://<VISION_SERVER_IP>:8554/<STREAM_NAME>.
  • go2rtc continuously sees a producer.
  • A WebRTC card on the dashboard can display video much closer to real time.

However, a small amount of normal latency can still come from:

  • The codec, such as H.265.
  • Wi-Fi / LAN.
  • Browser decoding.
  • The go2rtc/WebRTC pipeline.
  • CPU performance of the Video Worker.

This approach does not mean latency becomes zero. Its purpose is to eliminate the large accumulated delay of several seconds or minutes caused by the cloud path.

21. สรุปสั้น21. Short summary

ปัญหาเดิมคือกล้อง Xiaomi รุ่นเก่าไม่มี RTSP local ที่ Home Assistant ใช้ได้ตรง ๆ จึงต้องดูผ่าน cloud/P2P/HLS path ซึ่งมี buffer หลายชั้นและเกิด delay สะสม

วิธีแก้คือแยกเครื่อง Video Worker มารัน bridge ที่คุยกับ Xiaomi แล้ว publish วิดีโอออกมาเป็น RTSP local ผ่าน go2rtc จากนั้นให้ Home Assistant dashboard ดู RTSP/WebRTC จาก local network แทน cloud path เดิม

ผลคือภาพ live เสถียรขึ้น delay ต่ำลง และลดปัญหาดีเลย์สะสมอย่างมาก

The original problem is that older Xiaomi cameras may not provide direct local RTSP that Home Assistant can use. As a result, viewing has to pass through a cloud/P2P/HLS path with multiple buffering layers, which can cause accumulated delay.

The solution is to use a separate Video Worker running a bridge that communicates with Xiaomi and publishes the video as local RTSP through go2rtc. Home Assistant then displays RTSP/WebRTC from the local network instead of using the original cloud path.

The result is a more stable live view, lower latency, and a major reduction in accumulated delay.
